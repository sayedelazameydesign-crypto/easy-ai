# Cela.sh — Interoperability Architecture Baseline

> **الحالة:** مسودة معمارية للمراجعة البشرية؛ ليست دليلًا على وجود API عامة أو
> اعتماد GraphQL أو موصلات خارجية.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** عقود التكامل بين Cela.sh والعملاء والأنظمة الخارجية باستخدام معايير
> مفتوحة، دون إضافة ناقل أو مزود أو خدمة جديدة.

## 1. القرار المعماري

الواجهة الأساسية المقترحة للإصدار الأول هي **HTTP API بأسلوب REST وJSON**، لأنها
تطابق الـBackend الحالي وتقلل التعقيد التشغيلي. لا يُعتمد GraphQL أو gRPC أو
WebSocket أو MCP أو وسيط رسائل دون حاجة مثبتة ومراجعة مستقلة.

الهدف ليس إنشاء API عامة الآن، بل تعريف الشروط التي تمنع اقتران العملاء بالتنفيذ
الداخلي:

1. عقود موحدة وقابلة للتحقق والإصدار.
2. معايير نقل وترميز وهوية مفتوحة ومدعومة.
3. أخطاء وpagination وidempotency متسقة.
4. توافق خلفي ومسار إهلاك واضح.
5. توثيق آلي قدر الإمكان دون الادعاء بأن الوصف يثبت التنفيذ.

تظل المصادقة والاستضافة وحدود الاستخدام ونطاق API العامة `NOT_DECIDED`، ولذلك
يبقى النشر العام `BLOCKED`.

## 2. المبادئ

- **Contract first:** يراجع العقد قبل توسيع السطح العام، ثم يطابقه التنفيذ والاختبار.
- **أقل سطح عام:** لا يُكشف endpoint أو field بلا حالة استخدام ومالك وسياسة بيانات.
- **Open standards:** تفضيل مواصفات منشورة وقابلة للتنفيذ بأكثر من أداة.
- **التمثيل مستقل عن التخزين:** لا تعرض الجداول أو أسماء المزود الداخلية كعقد API.
- **الفشل صريح:** لا 200 مع خطأ مخفي، ولا fallback تجريبي يوصف كاستجابة حقيقية.
- **الأمن افتراضي:** authentication وauthorization والحصة جزء من العقد لا إضافات.
- **التوافق مقصود:** التغيير غير المتوافق يحتاج إصدارًا وانتقالًا موثقًا.
- **لا بروتوكول احترازي:** كل تقنية جديدة تحل حاجة مقاسة لا احتمالًا مستقبليًا.

## 3. حدود API

### 3.1 السطح الحالي

الـBackend الحالي يوفر عقد دردشة محليًا، لكنه لا يُعد API عامة جاهزة. قبل وصف أي
endpoint بأنه عام يجب توثيق:

- الغرض والمستهلكون والمالك.
- طريقة HTTP والمسار والإصدار.
- نموذج الطلب والاستجابة والقيود.
- المصادقة والصلاحية المطلوبة.
- idempotency والآثار الجانبية.
- المهل والحصة والتكلفة.
- الأخطاء وسياسة retry.
- تصنيف البيانات والاحتفاظ والتسجيل.
- SLO ودعم الإصدار وإهلاكه.

### 3.2 فصل الطبقات

```text
External Client
    │ HTTPS + versioned API contract
    ▼
API Boundary
    │ authentication, validation, authorization, quota
    ▼
Application Contract
    │ provider-neutral commands/results
    ▼
Adapters
    ├── Model provider
    ├── Persistence
    └── Approved tool connectors
```

لا يرى العميل SDK المزود أو أخطاءه الخام أو schema التخزين. استبدال المزود أو
قاعدة البيانات لا يغير العقد العام إلا بقرار إصدار صريح.

## 4. REST وHTTP

### 4.1 القواعد الأساسية

- HTTPS إلزامي لأي اتصال غير محلي وفق `SECURITY_ARCHITECTURE.md`.
- تستخدم الموارد أسماء nouns مستقرة، ولا تُحول كل دالة داخلية إلى endpoint.
- طرق HTTP تحافظ على دلالاتها: GET للقراءة دون أثر، POST للإنشاء/الأوامر، PUT
  للاستبدال idempotent، PATCH للتعديل الجزئي الموثق، DELETE للحذف.
- status codes تعكس النتيجة الفعلية؛ لا 200 عند فشل العملية.
- `Content-Type: application/json` و`Accept` واضحان، مع UTF-8 وفق معيار JSON.
- timestamps بصيغة RFC 3339/ISO 8601 مع timezone صريحة ويفضل UTC.
- المعرفات opaque strings؛ لا يستنتج العميل منها الترتيب أو نوع التخزين.
- الأرقام المالية لا تُمثل بـfloating point في العقود الحساسة؛ توثق الوحدة والدقة.

### 4.2 أكواد الحالة

الحد الأدنى المتسق:

- `200` نجاح قراءة أو أمر متزامن.
- `201` مورد أُنشئ، مع `Location` عند ملاءمته.
- `202` قبول غير متزامن فقط عند وجود job contract فعلي؛ ليس نجاحًا نهائيًا.
- `204` نجاح بلا جسم.
- `400` طلب غير صالح تركيبيًا.
- `401` مصادقة غائبة أو غير صالحة.
- `403` هوية معروفة بلا صلاحية.
- `404` مورد غير موجود أو مخفي وفق سياسة منع enumeration.
- `409` تعارض حالة أو idempotency.
- `413` حمولة أكبر من الحد.
- `415` نوع محتوى غير مدعوم.
- `422` حمولة سليمة تركيبيًا لكنها تخالف قواعد المجال، إذا اعتمد هذا التفريق.
- `429` حصة أو معدل، مع `Retry-After` عندما تكون إعادة المحاولة ممكنة.
- `500` خطأ داخلي غير متوقع.
- `502/503/504` فشل اعتماد أو عدم توافر أو انتهاء مهلة بحسب الحد المسؤول.

التفريق النهائي بين 400 و422 وبين 502/503/504 يحتاج اختبارات عقد موحدة؛ لا يكشف
أي منها جسم خطأ المزود أو stack trace.

## 5. نموذج الخطأ الموحد

النموذج المقترح يستلهم RFC 9457 (Problem Details for HTTP APIs):

```json
{
  "type": "https://cela.sh/problems/rate-limit",
  "title": "Request limit exceeded",
  "status": 429,
  "code": "rate_limited",
  "detail": "Try again later.",
  "request_id": "opaque-correlation-id"
}
```

القواعد:

- `code` ثابت ومقروء آليًا؛ `title` و`detail` للعرض ولا يبني العميل منطقه عليهما.
- `type` URI توثيقي ثابت عند نشر نطاق رسمي؛ المثال أعلاه ليس endpoint منفذًا.
- validation errors يمكن أن تضيف قائمة حقول بمسارات عامة، دون قيم حساسة.
- `request_id` للتتبع فقط ولا يمنح هوية أو صلاحية.
- لا أسرار أو prompts أو SQL أو stack traces أو أجسام مزود.
- localization في طبقة العرض؛ الأكواد لا تتغير بتغير اللغة.

اعتماد RFC 9457 وتفاصيل الامتدادات: `PROPOSED` حتى مراجعة التنفيذ الحالي.

## 6. مخططات البيانات والتحقق

- JSON هو التمثيل الافتراضي للعقود النصية.
- JSON Schema معيار مرشح للتحقق وإعادة استخدام النماذج داخل OpenAPI.
- `additionalProperties` يُحدد صراحة بحسب العقد، لا يترك للسلوك الافتراضي الغامض.
- required/nullable/optional مفاهيم منفصلة وموثقة.
- enums العامة لا تتوسع دون تقييم العملاء الذين قد يفشلون عند قيمة جديدة.
- الحدود تشمل الطول والحجم والعدد والنطاق والتنسيق، وتُطبق خادميًا.
- التطبيع لا يغير بيانات المستخدم صامتًا؛ توثق قواعد Unicode والمسافات عند الحاجة.
- binary data لا يُحشر داخل JSON بلا حاجة؛ يحدد media type وحد الحجم وطريقة الفحص.

يجب توليد أمثلة من fixtures منقحة أو صناعية، لا من بيانات إنتاج أو أسرار.

## 7. OpenAPI والتوثيق

OpenAPI 3.1 هو الخيار المقترح لوصف REST API لأنه يتوافق مع JSON Schema الحديثة.
قبل اعتماده يلزم:

- اختيار مصدر الحقيقة: spec-first أو code-first، دون ملفين يتباعدان.
- lint للوثيقة واختبارات تطابق contract مع التنفيذ.
- أمثلة طلب/استجابة وأخطاء ومصادقة وحدود.
- إخفاء endpoints داخلية من الوثائق العامة.
- تثبيت إصدار generator إن استُخدم ومراجعة الناتج قبل نشره.
- نشر documentation artifact فقط مع الإصدار الذي يصفه.

لا يوجد حاليًا ملف OpenAPI معتمد، ولا client SDK مولد، ولا developer portal؛ حالتها
`NOT_IMPLEMENTED`. إضافة generator dependency تحتاج دفعة مستقلة ومبررًا.

## 8. إصدار العقود والتوافق

### 8.1 سياسة الإصدار

الخيار المقترح للإصدار العام الأول هو major version في المسار مثل `/api/v1` مع
تغييرات متوافقة داخله. الشكل النهائي: `NOT_DECIDED` حتى اعتماد API عامة.

تغييرات متوافقة غالبًا:

- إضافة field اختياري لا يغير معنى الموجود.
- إضافة endpoint جديد مستقل.
- توسيع limits لصالح العميل مع بقاء الموارد والتكلفة آمنة.

تغييرات قد تكون غير متوافقة:

- حذف/إعادة تسمية field أو تغيير نوعه أو دلالته.
- جعل field اختياري required.
- تغيير status/error code الذي يعتمد عليه العميل.
- تضييق limits أو تغيير ordering/pagination.
- إضافة enum value لعميل غير tolerant.

### 8.2 الإهلاك

- إعلان deprecation في الوثائق والاستجابة عند اعتماد ترويسات مناسبة.
- تحديد بديل وتاريخ توقف ومالك وقائمة مستهلكين.
- قياس استخدام الإصدار القديم قبل إزالته مع احترام الخصوصية.
- فترة انتقال تعتمد العقود والدعم، ولا تُخترع قبل معرفة المستهلكين.
- لا endpoint دائم “مؤقت” بلا خطة إزالة.

لا يُحذف عقد مستخدم دون migration واختبارات توافق وموافقة بشرية.

## 9. Pagination والبحث والفرز

- كل collection غير محدودة تحتاج pagination وحدًا أعلى لحجم الصفحة.
- cursor pagination مفضلة للبيانات المتغيرة؛ offset مقبول لمجموعات صغيرة مستقرة
  مع توثيق عيوب التكرار/الفقد.
- cursor opaque وموقع ومحدود الصلاحية عند احتوائه حالة حساسة.
- ordering ثابت ويشمل tie-breaker واضحًا.
- allowlist لحقول filter/sort؛ لا تمرير تعبيرات خام إلى قاعدة البيانات.
- total count اختياري إذا كان مكلفًا، ويُوثق إن كان تقريبيًا.
- search semantics واللغة والتطبيع تُحدد قبل عرض البحث كعقد عام.

شكل pagination النهائي: `NOT_DECIDED` لأنه يعتمد موارد API التي لم تُعتمد بعد.

## 10. Idempotency والتزامن

- GET/PUT/DELETE تحافظ على دلالات idempotency المتوقعة ضمن العقد الموثق.
- POST ذو أثر مالي أو خارجي يقبل `Idempotency-Key` عندما يمكن تكراره بسبب الشبكة.
- المفتاح مرتبط بالهوية والعملية وبصمة الطلب ومدة احتفاظ محددة.
- إعادة المفتاح بحمولة مختلفة تُرفض بتعارض صريح.
- نتيجة مجهولة لعملية غير idempotent لا تُعاد تلقائيًا.
- optimistic concurrency يستخدم version/ETag و`If-Match` عند احتمال lost updates.
- لا ادعاء exactly-once عبر الشبكة؛ deduplication والتسوية موثقان.

مخزن idempotency الموزع ومدة الاحتفاظ: `NOT_DECIDED` قبل اختيار التخزين.

## 11. المصادقة والتفويض

- لا API عامة مجهولة وغير محدودة.
- OIDC/OAuth 2.1 أو جلسة خادمية آمنة خيارات مرشحة وفق نوع العميل.
- service-to-service credentials مستقلة، قصيرة العمر حيث أمكن، وأقل صلاحية.
- API keys إن لزمت لا تُعامل كهوية مستخدم كاملة، وتحتاج scopes وrotation وإبطالًا.
- permission tuple يبقى `(tenant, capability, operation, resource)` مع
  deny-by-default وفق `COMMUNICATION_ARCHITECTURE.md`.
- CORS لا يثبت هوية ولا يمنع عميلًا غير متصفح.
- بيانات الاعتماد لا تدخل query strings أو logs أو أمثلة الوثائق.

نظام الهوية والـscopes وdeveloper onboarding: `NOT_DECIDED`.

## 12. الحدود والحصة والتكلفة

كل API contract يوثق:

- أقصى body وحقل وقائمة وملف.
- timeout/deadline والسلوك عند الإلغاء.
- معدل وحصة متوقعة لكل هوية/tenant/operation.
- حدود tokens والإنفاق المستقلة.
- semantics لـ429 و`Retry-After`.
- هل retry آمن، وتحت أي idempotency key.

rate limiter داخل process غير كافٍ لخدمة متعددة النسخ. الحد الموزع وhard cost cap
وkill switch موانع إطلاق عام، ولا تستبدلها CORS أو ترويسة IP قابلة للتزوير.

## 13. GraphQL

GraphQL معيار مفتوح مفيد عندما يحتاج عملاء متعددون projections وعلاقات مختلفة،
لكنه **ليس معتمدًا** لهذا المشروع الآن. قبل اعتماده يجب إثبات:

- أن REST يسبب over-fetching/under-fetching ملموسًا لا مجرد تفضيل.
- schema ownership وإصدار الحقول وإهلاكها.
- field-level authorization ومنع تسريب tenant.
- depth/complexity/cost limits ومنع الاستعلامات المكلفة.
- pagination وN+1 mitigation وDataLoader-equivalent عند الحاجة.
- persisted queries أو allowlisting للسطوح الحساسة.
- introspection policy، logging المنقح، والحصة المالية لاستدعاءات النموذج.
- monitoring وcaching واختبارات عقد مستقلة.

حالة GraphQL: `DEFERRED / NOT_APPROVED`. لا يقدم ميزة لمجرد أنه معيار مفتوح، وقد
يوسع سطح الهجوم والتكلفة إذا أضيف دون نموذج استعلام حقيقي.

## 14. Webhooks والأحداث

لا webhooks أو event API منفذة حاليًا. إذا ظهرت حاجة مثبتة:

- HTTPS destination مع allowlist وسياسة SSRF/DNS rebinding قبل URLs ديناميكية.
- توقيع HMAC أو معيار مناسب مع timestamp وreplay window وrotation.
- event ID وtype وversion وoccurred_at وtenant context غير حساس.
- at-least-once delivery، retries محدودة، وdeduplication لدى المستهلك.
- ترتيب غير مضمون إلا إذا نُص عليه ضمن partition محدد.
- endpoint verification وإيقاف تلقائي للوجهات الفاشلة.
- payload أقل ما يمكن، مع روابط وصول مصادق بدل بيانات حساسة كبيرة.
- replay يدوي مصرح ومسجل، وdead-letter policy إذا اعتمد broker لاحقًا.

لا message broker أو webhook delivery service قبل حاجة وموافقة معمارية.

## 15. استيراد وتصدير البيانات

- صيغ التبادل المرشحة: JSON للكيانات المهيكلة وCSV للبيانات الجدولية البسيطة وفق
  RFC 4180 مع توثيق encoding/header/formula-injection protection.
- export له schema version ووقت إنشاء ومصدر وتصنيف وchecksum عند الحاجة.
- الاستيراد يتحقق قبل commit، ويدعم dry-run/validation report للعمليات الكبيرة.
- حدود حجم وعدد وسجل أخطاء دون إعادة القيم الحساسة.
- لا قبول serialized objects خاصة بلغة البرمجة من جهات غير موثوقة.
- حذف/نقل البيانات يخضع لسياسة الخصوصية والاحتفاظ والصلاحية والتدقيق.

لا export/import عام معتمد حتى تحديد نموذج البيانات والهوية.

## 16. SDKs والعملاء

لا يُولد SDK قبل استقرار عقد API وحاجة مستهلك فعلية. عند اعتماده:

- يُولد من spec مثبت الإصدار أو يختبر ضده.
- retries لا تعمل افتراضيًا للكتابات غير الآمنة.
- timeouts مطلوبة وقابلة للضبط ضمن سقف.
- أخطاء typed تحافظ على `code` و`request_id` دون أسرار.
- semantic versioning وchangelog وسياسة دعم runtimes.
- أمثلة لا تحتوي مفاتيح ولا تشجع تعطيل TLS.
- conformance tests بلغة مستقلة عن implementation عند الإمكان.

SDK ليس بديلًا لتوثيق HTTP contract؛ العملاء يظلون قادرين على استخدام المعيار
المفتوح مباشرة.

## 17. اختبار قابلية التشغيل البيني

قبل وصف API بأنها عامة يلزم:

- schema validation لطلبات واستجابات success والأخطاء.
- contract tests بين الـspec والتنفيذ.
- negative tests للأنواع والحدود والحقول المجهولة والمصادقة والصلاحيات.
- compatibility tests لعميل الإصدار السابق عند تغيير متوافق مزعوم.
- idempotency وconcurrency وpagination tests.
- locale/Unicode/timezone tests.
- اختبار عميل مستقل عن Python وعميل JavaScript على الأقل عند وجود استهلاك حقيقي.
- fuzz/property tests للـparsers الحساسة ضمن حدود آمنة.
- security tests للـBOLA/IDOR وmass assignment وinjection وrate limits.
- اختبار OpenAPI examples آليًا إن اعتمدت الوثيقة.

mock يثبت عقد التطبيق فقط. لا اختبار مزود أو نظام خارجي دون تصريح ومفتاح وحد مالي.
غياب الاختبار يعني `NOT_TESTED`.

## 18. الرصد والدعم

- metrics حسب API version وoperation وstatus class دون user IDs عالية الكثافة.
- قياس latency وerrors و429 وحجم الحمولة واستخدام العقود المهملة.
- correlation ID من حد موثوق؛ لا ثقة عشوائية بترويسة عميل.
- logs منقحة ولا تحتوي tokens أو bodies افتراضيًا.
- runbook لكل dependency وerror budget وفق وثيقة الموثوقية.
- status page وsupport channel وSLA: `NOT_DECIDED`، ولا تُعلن قبل ملكية تشغيلية.

## 19. سجل القرارات

| القرار | الحالة | المطلوب للحسم |
|---|---|---|
| REST/JSON كأساس الإصدار الأول | `PROPOSED` | مراجعة بشرية وعقد API معتمد |
| OpenAPI 3.1 | `PROPOSED` | اختيار مصدر الحقيقة وأداة تحقق خفيفة |
| RFC 9457 للأخطاء | `PROPOSED` | مواءمة taxonomy الحالية واختبارات عقد |
| مسار `/api/v1` | `NOT_DECIDED` | اعتماد السطح العام وسياسة الإصدار |
| JSON Schema | `PROPOSED` | توافق أدوات التنفيذ وOpenAPI |
| OIDC/OAuth 2.1 | `NOT_DECIDED` | اختيار الهوية وأنواع العملاء |
| GraphQL | `DEFERRED / NOT_APPROVED` | حاجة استعلام مثبتة وضوابط تكلفة وأمن |
| Webhooks | `NOT_APPROVED` | مستهلك فعلي ونموذج SSRF وتوقيع وتسليم |
| SDKs مولدة | `NOT_APPROVED` | عقد مستقر وحاجة عملاء فعلية |
| API عامة | `BLOCKED` | إغلاق بوابات القسم التالي |

## 20. بوابات الإطلاق

### مسموح الآن

- تطوير وتحسين عقد محلي محدود مع اختبارات عقد.
- كتابة OpenAPI draft في دفعة مستقلة دون نشره كواجهة عامة.
- استخدام JSON وHTTP القياسيين في الحدود الحالية.
- توثيق الأخطاء والقيود المنفذة دون تغيير عقود `sync/`.

### مانع لإطلاق API عامة

- السطح والإصدار والمالك والمستهلكون غير معتمدين.
- الهوية والصلاحيات والعزل متعدد المستأجرين غير منفذة ومختبرة.
- rate limit وحصة وتكلفة وkill switch موزعة غير منفذة.
- لا OpenAPI/JSON Schema معتمد ولا conformance tests.
- سياسة التوافق والإهلاك والدعم غير معتمدة.
- بوابات الأمن والموثوقية والتوسع لا تزال مفتوحة.
- لا اختبار اختراق مصرح للسطح العام.

### شرط تغيير الحالة

لا تصبح قابلية التشغيل البيني `APPROVED` بوجود endpoint أو وثيقة فقط. يلزم spec
محدد الإصدار، تنفيذ مطابق، اختبارات عقد وتوافق وأمن، عميل مستقل ينجح فعليًا، وموافقة
بشرية على الهوية والبيانات والتكلفة والدعم.

## 21. العلاقة مع الوثائق الأخرى

- `AI_BACKEND_DESIGN.md`: عقد النموذج والمزود وحدود tokens والتكلفة.
- `COMMUNICATION_ARCHITECTURE.md`: دلالات النقل والمهل والإلغاء والأخطاء.
- `SECURITY_ARCHITECTURE.md`: الهوية والتفويض والتشفير وSSRF والخصوصية.

أو استضافة أو ناقلًا جديدًا، ولا تغير بنية `sync/` أو حالات المزامنة أو manifest.
