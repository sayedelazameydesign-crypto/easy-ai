# Cela.sh — Maintainability Engineering Baseline

> **الحالة:** مسودة هندسية للمراجعة البشرية؛ ليست شهادة جودة ولا دليلًا على تغطية
> اختبارية شاملة.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** قواعد صيانة الشيفرة والتبعيات والتوثيق والاختبارات وعمليات التغيير.

## 1. القرار الهندسي

سهولة الصيانة نتيجة حدود واضحة وتغييرات صغيرة واختبارات ذات معنى، وليست نتيجة إطار
عمل جديد أو كثرة التعليقات. يبقى المشروع بتقنياته الحالية البسيطة ما لم تثبت حاجة
تستحق كلفة الهجرة:

- واجهة HTML/CSS وJavaScript دون framework.
- Backend وقناة مزامنة بلغة Python.
- اختبارات Python وJavaScript الحالية.
- GitHub Actions للبناء والفحص والنشر القائم.

تعتمد هذه الوثيقة **modular monolith** كما في `SCALABILITY_ARCHITECTURE.md`، وتحظر
إعادة كتابة عامة أو تغيير عقود `sync/` لمجرد “التحديث”. أي ترقية أو refactor يجب أن
تكون قابلة للمراجعة والاختبار والرجوع.

## 2. مبادئ الكود القابل للصيانة

1. **الوضوح قبل الاختصار:** أسماء تصف النية وتدفق تحكم مباشر.
2. **مسؤولية محددة:** كل وحدة ودالة لها سبب تغيير مفهوم.
3. **عقود صريحة:** المدخلات والمخرجات والأخطاء والآثار الجانبية موثقة ومختبرة.
4. **فشل صريح:** لا fallback صامت ولا نجاح زائف.
5. **التعقيد عند الحاجة فقط:** لا abstraction أو dependency بلا حالة استخدام حالية.
6. **الأمان جزء من العقد:** validation والصلاحيات والتنقيح لا تُضاف لاحقًا كطبقة
   تجميلية.
7. **تغيير صغير:** كل دفعة تعالج غرضًا واحدًا ولا تخلط الواجهة والنشر والبنية دون
   ضرورة.
8. **مصدر حقيقة واحد:** لا تكرار لقواعد الأعمال بين الواجهة والـBackend والوثائق.

## 3. تنظيم الشيفرة وحدود المسؤولية

### 3.1 الحدود الحالية

- `backend/`: حدود HTTP وإعدادات الخادم وprovider adapter.
- `sync/`: قناة المزامنة بعقودها الحالية؛ لا تُعاد هيكلتها ضمن تحسينات غير مرتبطة.
- `js/`: سلوك الواجهة وعقد الاتصال وحالة العرض.
- `tests/`: اختبارات Python بحسب السلوك والوحدة.
- `tests-js/`: اختبارات JavaScript دون إضافة framework ثقيل تلقائيًا.
- `scripts/`: مهام بناء أو تحقق قابلة للتشغيل وغير مخفية داخل CI فقط.
- `docs/`: التصميم والتشغيل والقرارات غير المنفذة بوسم صريح.

### 3.2 قواعد الاعتماد

- منطق المجال لا يعتمد مباشرة على HTTP أو SDK مزود خارجي.
- تُحصر قراءة environment variables في طبقة config موثقة.
- لا globals قابلة للتغيير لحالة المستخدم أو الحصة أو الجلسة.
- لا circular imports ولا imports ذات آثار شبكة أو كتابة عند التحميل.
- يُحقن الوقت والعشوائية والاتصال الخارجي عندما تحتاج الاختبارات التحكم فيها.
- لا تنسخ دالة validation نفسها بين عدة مسارات؛ يُعاد استخدامها عبر وحدة محددة.
- لا helper عام باسم مبهم؛ يبقى قرب المجال حتى يثبت أنه مشترك.

### 3.3 حجم وتعقيد الوحدات

لا تفرض هذه الوثيقة أرقامًا عمياء لعدد الأسطر. عند ظهور دالة أو ملف كبير يُفصل فقط
وفق مسؤوليات وعقود طبيعية. إشارات تستدعي المراجعة:

- مستويات تداخل كثيرة أو فروع يصعب تعدادها.
- معامل boolean يغير معنى الدالة جذريًا.
- آثار جانبية متعددة غير قابلة للعزل.
- تعديل واحد يتطلب تغييرات متكررة في ملفات غير مرتبطة.
- اختبار الوحدة يحتاج إعدادًا واسعًا لفحص سلوك صغير.

قرار الفصل يرفق باختبارات تحفظ السلوك، ولا يتحول إلى إعادة تسمية واسعة بلا قيمة.

## 4. أسلوب الكود والتوثيق داخله

- يتبع Python أسلوب PEP 8 وtype hints عند حدود الوحدات والعقود العامة.
- يتبع JavaScript صياغة حديثة مدعومة في المتصفحات المستهدفة دون transpiler ما لم
  تثبت الحاجة.
- أسماء اللغة الإنجليزية للشيفرة والعقود؛ النص العربي/الإنجليزي للمستخدم يبقى في
  طبقة i18n.
- docstrings للواجهات العامة والمنطق غير البديهي، وتشرح العقد لا إعادة صياغة السطر.
- التعليق يوضح **لماذا** والقيد أو الخطر، لا **ماذا** تفعل صياغة واضحة أصلًا.
- TODO يتضمن سببًا وشرط إغلاق ومرجع issue عندما تتوفر عملية issues؛ لا TODO دائم
  بلا مالك.
- لا كود معلق أو نسخ قديمة داخل comments؛ التاريخ محفوظ في Git.
- رسائل الخطأ مستقرة وآمنة وقابلة للاختبار، ولا تكشف أسرارًا أو أجسام مزود.

### التنسيق والتحليل الساكن

اختيار formatter/linter/type checker وحصد baseline الحالي: `NOT_DECIDED`. قبل
إضافتها يجب:

1. تقييم أداة خفيفة ومدعومة توافق Python وJavaScript الحاليين.
2. فصل دفعة التنسيق الشامل عن التغييرات السلوكية.
3. تثبيت الإصدار في CI والتطوير.
4. منع القواعد المتضاربة أو auto-fix الذي يغير السلوك.
5. اعتماد تدريجي لا يخفي أخطاء جديدة خلف آلاف التحذيرات القديمة.

لا تدعي الوثيقة وجود lint أو type-check gate حاليًا.

## 5. التقنيات الحديثة والمدعومة

“حديث” يعني إصدارًا مدعومًا أمنيًا ومتوافقًا مع بيئة التشغيل، لا أحدث إصدار يوم
صدوره.

### سياسة runtimes

- يُحدد إصدار Python الأدنى والأقصى المدعومان في مكان قابل للتنفيذ، ثم تُختبر
  المصفوفة المعتمدة في CI.
- تُحدد المتصفحات المدعومة وفق استخدام فعلي، وتُراجع APIs قبل استعمالها.
- لا تعتمد ميزة تجريبية أو runtime غير مدعوم طويلًا في الإنتاج.
- ترقية major تحتاج مراجعة breaking changes وخطة rollback واختبارات كاملة.
- إصدارات runtime المعتمدة الحالية وسياسة EOL: `NEEDS_VALIDATION`؛ ذكر Python
  3.11 في README لا يثبت وحده مصفوفة دعم كاملة.

### سياسة التبعيات

- أقل عدد ممكن من التبعيات المباشرة.
- كل dependency لها غرض ومالك ومصدر رسمي وترخيص مقبول.
- حدود الإصدارات الحالية في `requirements.txt` ليست lockfile ولا تضمن build قابلًا
  للتكرار؛ استراتيجية pinning/lock والحزم الانتقالية: `NOT_DECIDED`.
- تحديثات patch/minor تمر عبر الاختبارات والفحص الأمني؛ major بدفعة مستقلة.
- dependency غير مصانة أو ذات ثغرة غير معالجة تُستبدل أو تُعزل أو يُقبل خطرها
  صراحة.
- لا framework أو خدمة مدفوعة أو SDK ثقيل دون مقارنة كلفة وفائدة.
- لا تثبيت من URL عشوائي أو branch متحرك في الإنتاج.

### دورة التحديث

- فحص ثغرات التبعيات دوريًا وفي pull requests.
- مراجعة شهرية أو cadence يعتمدها الفريق للتحديثات غير الطارئة.
- تحديث أمني حرج يُفرز حسب التعرض الفعلي ويُعالج وفق SLA أمني معتمد.
- release notes وmigration guides الرسمية تُراجع قبل الترقية.
- لا يصف فشل scan بأنه نجاح؛ يُسجل كفحص لم يُنفذ أو فشل بوابة.

## 6. التوثيق الشامل

### 6.1 هرم التوثيق

- `README.md`: حقيقة المنتج الحالية، البدء السريع، والقدرات المنفذة فقط.
- `docs/SETUP.md`: إعداد وتشغيل قناة المزامنة القائمة.
- `SECURITY.md`: نموذج تهديد وضوابط القناة الحالية وسياسة الإبلاغ.
- `docs/*_ARCHITECTURE.md`: تصميمات مستقبلية وحالة القرارات والبوابات.
- docstrings/comments: عقود محلية وقيود لا تناسب وثيقة تشغيلية.
- runbooks: إجراءات تشغيل قابلة للتنفيذ بعد اختيار المنصة.
- ADRs: قرارات معمارية مقبولة، بدائلها وعواقبها.

يجب عدم نقل الحالة المقترحة إلى README كميزة منفذة قبل وجود دليل. الوثيقة التي
تصف المستقبل تحمل حالة `PROPOSED` أو `NOT_DECIDED` أو `BLOCKED` بوضوح.

### 6.2 الحد الأدنى لكل مكوّن

- الغرض والمالك وحدود المسؤولية.
- واجهة الاستخدام والمدخلات والمخرجات والأخطاء.
- configuration والأسرار المطلوبة بأسمائها فقط، لا قيمها.
- تخزين البيانات والاحتفاظ والحذف.
- الاعتماديات الخارجية والمهل والحصة والسلوك عند الفشل.
- طريقة الاختبار محليًا وفي CI.
- خطوات التشغيل والمراقبة والrollback عند انطباقها.
- القيود المعروفة والقرارات المؤجلة.

### 6.3 منع تقادم الوثائق

- تحديث الوثيقة في نفس دفعة تغيير العقد أو السلوك.
- أمثلة الأوامر تُنفذ في CI حيث يكون ذلك آمنًا وعمليًا.
- أعداد الاختبارات والإصدارات المتغيرة لا تُكرر يدويًا دون آلية تحديث؛ العدد الحالي
  في README يحتاج مراجعة عند كل تغيير للاختبارات.
- الروابط والمسارات تُفحص دوريًا دون إرسال أسرار أو طلبات غير مصرح بها.
- مراجعة ربع سنوية مقترحة لسجلات القرارات والصفحات التشغيلية؛ المالك والجدول
  الفعليان `NOT_DECIDED`.

## 7. سجل القرارات المعمارية (ADR)

عند قبول قرار مؤثر، يُنشأ ADR صغير يتضمن:

- العنوان والتاريخ والحالة: proposed/accepted/superseded/rejected.
- السياق والقيود والمتطلبات غير الوظيفية.
- الخيارات المدروسة ومصادر الحقائق.
- القرار ومن وافق عليه.
- الآثار الإيجابية والسلبية والمخاطر.
- خطة التحقق والrollback أو migration.

لا يُستخدم ADR لإخفاء قرار لم يُتخذ؛ تبقى السجلات الحالية `NOT_DECIDED` حتى موافقة
بشرية. لا حاجة لأداة إدارة ADR أو dependency جديدة.

## 8. استراتيجية الاختبارات الآلية

### 8.1 طبقات الاختبار

- **Unit:** منطق خالص سريع، حالات الحدود والأخطاء، دون شبكة أو وقت فعلي.
- **Contract:** ثبات عقود HTTP وprovider adapter وmanifest والأخطاء.
- **Integration:** تعاون مكونات حقيقية محليًا مع بدائل محدودة للخدمات الخارجية.
- **System/E2E:** رحلة مستخدم عبر artifact أو خادم مماثل للإنتاج.
- **Security:** validation والتفويض والتنقيح والأسرار وSSRF والحدود.
- **Reliability:** timeout وretry والإلغاء وidempotency والاستعادة.
- **Performance:** baseline وحمل وsoak وفق وثيقة قابلية التوسع.

ليست كل حالة مناسبة لـE2E. يُفضل أدنى طبقة تثبت السلوك دون فقد الثقة.

### 8.2 جودة الاختبار

- اسم الاختبار يصف السلوك والشرط والنتيجة.
- Arrange/Act/Assert واضح أو بنية مكافئة.
- لا شبكة عامة أو حسابات حقيقية في الاختبارات الافتراضية.
- fixtures صغيرة وغير حساسة ولا تشبه أسرارًا حقيقية إلا عند اختبار scanner داخل
  نطاق معروف.
- التحكم في الوقت والعشوائية؛ لا sleeps لتجاوز race conditions.
- لا assertions شكلية مثل “لا يرمي استثناء” عندما توجد نتيجة محددة.
- اختبار regression يفشل قبل الإصلاح وينجح بعده متى كان ذلك ممكنًا.
- mocks تثبت عقد التطبيق فقط، ولا تثبت سلوك المزود أو الاستضافة.
- لا snapshot ضخم يخفي فروقًا مهمة؛ تُراجع snapshots ككود.

### 8.3 التغطية

نسبة coverage وحدها لا تثبت الجودة. قبل فرض حد رقمي يجب قياس baseline وتحديد
الأجزاء الحرجة. المتطلبات النوعية:

- كل عقد عام له happy path وحالات validation والفشل الأساسية.
- فروع الأمن والتكلفة والخصوصية تحتاج اختبارات سلبية صريحة.
- كل bug مُصلح يضيف regression test إن أمكن.
- الكود المستحيل اختباره إشارة لإعادة ضبط حدوده، لا لاستبعاده صامتًا.

Coverage baseline والحد الأدنى: `NOT_MEASURED`. لا يجوز وصف المجموعة بأنها شاملة
قبل قياس الفجوات وتشغيل طبقاتها بنجاح.

## 9. هرم التحقق في CI

بوابة pull request المرشحة، بعد اعتماد الأدوات:

1. فحص whitespace وملفات وأسرار ممنوعة.
2. syntax/format/lint والتحليل الساكن المعتمد.
3. unit وcontract tests السريعة.
4. integration tests المحلية.
5. build للـartifact وفحص أنه لا يحتوي أسرارًا أو ملفات محظورة.
6. security/dependency scan.
7. system smoke test على artifact معزول.

اختبارات الأداء أو المزود الحقيقي أو DR تعمل بجدول/تفويض وبيئة محدودة، لا على كل
PR ولا مع أسرار متاحة لفروع غير موثوقة. بوابة فاشلة لا تُتجاوز بتعطيل الاختبار؛
يُصلح السبب أو يُقبل الاستثناء بمالك ومدة ومبرر.

حالة CI الحالية تحتاج جردًا منفصلًا؛ وجود workflow لا يثبت نجاح كل طبقة أعلاه.

## 10. تصميم قابل للاختبار

- فصل parsing/validation عن I/O.
- provider وstorage خلف عقود صغيرة بدل monkeypatch داخلي واسع.
- تمرير dependencies بوضوح دون service locator عالمي.
- نتائج وأخطاء محددة بدل طباعة داخل منطق المجال.
- clock وID generator قابلان للتحكم عند الحاجة.
- server startup منفصل عن إنشاء التطبيق كي يمكن اختباره دون فتح port.
- JavaScript يفصل DOM rendering عن قرار الاتصال والحالة بقدر يخدم الاختبار.

لا تُعاد كتابة الوحدات الحالية دفعة واحدة لتحقيق ذلك؛ تُحسن الحدود عند تعديل
السلوك المرتبط، مع characterization tests قبل refactor عالي المخاطر.

## 11. المراجعة وإدارة التغيير

كل دفعة يجب أن توضح:

- المشكلة والنطاق وما هو خارج النطاق.
- السلوك السابق والجديد وخطة الاختبار.
- أثر البيانات والأمن والتكلفة والتوافق.
- migration وrollback إن وُجدا.
- تحديث الوثائق والعقود.

قواعد المراجعة:

- لا خلط تنسيق شامل مع إصلاح وظيفي.
- لا merge عند فشل CI أو غياب موافقة مطلوبة.
- الملفات الحساسة مثل workflows والأمن والتشفير تحتاج reviewer مناسبًا.
- generated files تُعرف وتُراجع عبر مصدرها، ولا تعدل يدويًا إذا كانت مولدة.
- commits صغيرة ذات رسائل تصف النية؛ لا force-push أو تاريخ معاد كتابته دون حاجة
  وتنسيق.

## 12. التوافق والإهلاك

- العقود العامة تُصدر بإصدار واضح عند بدء مستخدمين خارجيين.
- الإضافة المتوافقة تسبق الحذف، مع فترة إهلاك واتصال للمستهلكين.
- لا تغيير صامت لمعاني error codes أو manifest أو حالات المزامنة.
- migration للبيانات قابلة لإعادة التشغيل أو لها guard وحالة واضحة.
- feature flags مؤقتة بمالك وتاريخ إزالة واختبارات للحالتين.
- إزالة مسار قديم تشمل الشيفرة والاختبارات والوثائق والقياسات المرتبطة.

## 13. قياس قابلية الصيانة

مؤشرات مرشحة دون تحويلها إلى أهداف شكلية:

- lead time من تغيير مراجع إلى نشر معتمد.
- change failure rate ووقت استعادة التغيير.
- flaky test rate ومدة CI.
- عمر التبعيات والثغرات المفتوحة.
- bugs المتكررة في نفس الحد.
- وقت onboarding لتشغيل الاختبارات وفهم مكوّن.
- نسبة تغييرات العقود التي حدثت معها الوثائق والاختبارات.

لا تُكافأ زيادة عدد الاختبارات أو الأسطر وحدها. القيم الأساسية والمالكون والأهداف:
`NOT_DECIDED`.

## 14. سجل القرارات والفجوات

| القرار | الحالة | المطلوب للحسم |
|---|---|---|
| modular monolith كبداية | `PROPOSED` | مراجعة بشرية وحدود تدريجية |
| Python support matrix | `NEEDS_VALIDATION` | runtime رسمي وCI matrix |
| browser support matrix | `NOT_DECIDED` | بيانات استخدام ومتطلبات منتج |
| formatter/linter/type checker | `NOT_DECIDED` | تقييم خفيف وbaseline مستقل |
| dependency lock strategy | `NOT_DECIDED` | توافق CI والتحديثات القابلة للتكرار |
| coverage baseline/threshold | `NOT_MEASURED` | تشغيل coverage وتحليل الأجزاء الحرجة |
| system/E2E harness | `NOT_DECIDED` | رحلات حرجة وبيئة مماثلة للإنتاج |
| docs/ADR ownership | `NOT_DECIDED` | مالك وجدول مراجعة |
| full maintainability gate | `NOT_IMPLEMENTED` | تنفيذ الأدوات والاختبارات والتحقق |

## 15. بوابات الجاهزية

### مسموح الآن

- تحسينات صغيرة تحفظ العقود وتضيف اختبارات حقيقية.
- characterization tests قبل refactor.
