# Cela.sh — User Experience & Responsive Design Baseline

> **الحالة:** مسودة تصميم وتجربة استخدام للمراجعة البشرية؛ ليست دليلًا على اجتياز
> اختبار قابلية استخدام أو اعتماد WCAG أو اكتمال دعم كل جهاز.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** مبادئ وقواعد واجهة الدردشة والقدرات الثنائية اللغة والاستجابة للأجهزة،
> دون إعادة تصميم بصري أو إضافة framework في هذه الدفعة.

## 1. القرار التصميمي

تُحسن الواجهة الحالية تدريجيًا بدل إعادة كتابتها. تبقى HTML/CSS وJavaScript البسيطة
هي الأساس ما دامت تحقق السلوك المطلوب، ولا يُضاف design system أو UI framework ثقيل
دون حاجة مثبتة.

الأولويات:

1. وضوح ما هو منفذ وما هو تجريبي أو غير متاح.
2. إكمال المهمة الأساسية بأقل عبء معرفي.
3. وصول كامل بلوحة المفاتيح وتقنيات المساعدة.
4. تكيف وظيفي مع الشاشات الصغيرة والتكبير واتجاه RTL، لا مجرد تصغير بصري.
5. استجابة إدراكية صادقة أثناء الانتظار والفشل والإلغاء.
6. أداء يحافظ على قابلية الاستخدام على أجهزة وشبكات محدودة.

هذه الوثيقة لا تحول الحالات المقترحة إلى ميزات منفذة. لا بث حي ولا حفظ محادثة ولا
رفع ملفات ولا صوت ما لم تُنفذ وتُختبر وتُعرض حالتها بصدق.

## 2. المستخدمون والمهام الأساسية

قبل تغيير كبير يجب تحديد مستخدمين فعليين وسياقهم، لا personas مختلقة. الفرضيات
الأولية التي تحتاج تحققًا:

- مستخدم عربي أو إنجليزي يريد فهم حالة المنتج بسرعة.
- مستخدم يرسل رسالة نصية ويحصل على رد تجريبي أو Backend حقيقي حسب الإعداد.
- مستخدم على هاتف أو شاشة صغيرة أو اتصال بطيء.
- مستخدم يعتمد لوحة المفاتيح أو قارئ شاشة أو تكبيرًا مرتفعًا.
- مشغل يحتاج تشخيص فشل آمن دون كشف أسرار للمستخدم.

الرحلة الأساسية:

1. فهم هل الدردشة Demo أم متصلة فعليًا.
2. إدخال الرسالة ومراجعتها.
3. إرسالها مرة واحدة ومنع الطلب المكرر.
4. رؤية حالة الانتظار وإمكانية الإلغاء عند تنفيذها.
5. قراءة الرد أو خطأ واضح مع خطوة تالية آمنة.
6. تبديل اللغة دون فقد الحالة أو تضليل حالة القدرات.

البحث مع مستخدمين فعليين وقياس نجاح المهمة: `NOT_PERFORMED`.

## 3. مبادئ قابلية الاستخدام

### 3.1 الوضوح والاتساق

- مصطلح واحد لكل مفهوم عبر العربية والإنجليزية.
- ترتيب وإشارات بصرية ثابتة للأفعال الأساسية والثانوية والخطرة.
- labels نصية للأيقونات غير البديهية؛ tooltip وحده غير كافٍ للمس واللوحة.
- لا زر يبدو قابلًا للنقر إذا كانت الميزة غير منفذة؛ يُعطل مع تفسير أو يُخفى فقط
  إذا لم يؤثر ذلك في فهم الحالة.
- الحالات Demo وAvailable وUnavailable مميزة بالنص، لا اللون فقط.
- لا أرقام استخدام أو نجاح أو زمن غير مقاسة.

### 3.2 تقليل العبء المعرفي

- المهمة الأساسية ظاهرة دون onboarding إلزامي.
- شاشة البداية تشرح باختصار نوع البيانات المتوقع وحدود الخدمة.
- progressive disclosure للإعدادات والتفاصيل المتقدمة.
- لا modal للرسائل المعلوماتية البسيطة.
- الخيارات الافتراضية آمنة وقابلة للفهم، ولا توافق ضمنيًا على حفظ البيانات.
- النصوص المختصرة لا تحذف أثرًا مهمًا مثل التكلفة أو المشاركة مع مزود خارجي.

### 3.3 التحكم ومنع الأخطاء

- زر الإرسال له حالة واضحة ولا يسمح بطلب مكرر أثناء الطلب الجاري.
- Enter/Shift+Enter موثقان ومتوافقان مع IME وإدخال العربية؛ لا إرسال أثناء
  composition.
- validation قريب من الحقل ويشرح التصحيح دون لوم المستخدم.
- لا تُمسح الرسالة عند فشل الطلب قبل ضمان إمكانية استعادتها.
- العمليات غير القابلة للعكس تحتاج تأكيدًا يصف الأثر، لا تأكيدًا لكل فعل بسيط.
- cancel وretry، عند تنفيذهما، يحترمان idempotency والمهلة والتكلفة.
- لا retry تلقائي خفي لعملية قد تُحاسب أو تحدث أثرًا خارجيًا.

## 4. بنية المعلومات والتنقل

- الصفحة لها heading رئيسي واحد وتسلسل headings منطقي.
- landmark regions واضحة: header/navigation/main/form/status/footer عند وجودها.
- الانتقال باللغة أو الحالة لا يعيد المستخدم لبداية الصفحة دون ضرورة.
- الروابط تصف وجهتها بدل “اضغط هنا”.
- deep links والعودة في المتصفح تُحترم عند ظهور صفحات/حالات متعددة مستقبلًا.
- لا يُحول كل إعداد إلى navigation item؛ تبقى المهمة الأساسية في المقدمة.
- breadcrumb غير مطلوب لتطبيق صفحة واحدة، ولا يضاف احترازيًا.

أي إعادة هيكلة للتنقل تحتاج card sort أو task test إذا ازداد عدد الشاشات فعليًا.

## 5. نموذج حالات الواجهة

كل قدرة تملك حالة صريحة مستقلة عن الشكل:

```text
unavailable → available-idle → submitting → success
                                  ├── validation-error
                                  ├── timeout
                                  ├── rate-limited
                                  ├── provider-error
                                  ├── cancelled
                                  └── offline/network-error
```

القواعد:

- لا تظهر success قبل تأكيد النتيجة الفعلية.
- loading ليس مؤشرًا بلا نهاية؛ يرتبط بمهلة ورسالة تالية.
- الخطأ لا يمحو المحتوى القابل للاستعادة.
- الحالة تُعلن لتقنيات المساعدة بطريقة غير مزعجة.
- timeout وrate limit وعدم المصادقة أخطاء مختلفة برسائل مختلفة.
- response stale أو المتأخر بعد الإلغاء لا يستبدل حالة أحدث.
- Demo لا يتحول صامتًا إلى بديل عند فشل Backend الحقيقي.

## 6. كتابة الواجهة والمحتوى

- لغة مباشرة ومحددة للفعل التالي.
- عنوان الخطأ يشرح ما حدث؛ النص يشرح ما يمكن للمستخدم فعله.
- لا أكواد داخلية وحدها، ويمكن إظهار `request_id` المنقح للاتصال بالدعم.
- لا وعود مثل “فوري” أو “دائمًا متاح” دون SLO وقياس.
- لا وصف ميزة بأنها AI حقيقية إذا كانت preset demo.
- التحذير الأمني لا يكشف تفاصيل قد تساعد مهاجمًا.
- النص العربي طبيعي وليس ترجمة حرفية، والإنجليزية تقابل المعنى والحالة.

يجب أن تخضع النصوص الحساسة للخصوصية والتكلفة والموافقة لمراجعة بشرية وقانونية عند
انطباقها.

## 7. التدويل وRTL

- العربية والإنجليزية متساويتان في keys والحالات والقدرات.
- يستخدم `dir="rtl"`/`ltr` وفق اللغة مع CSS logical properties مثل
  `margin-inline` و`padding-inline` بدل افتراض اليمين واليسار.
- اتجاه المحتوى المستقل مثل URL والكود والأرقام الطويلة يُعزل بـ`dir` مناسب أو
  Unicode bidi isolation دون تغيير البيانات.
- تبديل اللغة يحافظ على الرسالة الحالية وحالة الطلب متى كان ذلك آمنًا.
- لا تُترجم identifiers أو error codes أو أسماء المنتجات آليًا داخل العقد.
- تنسيق التاريخ والعدد عبر APIs معيارية مع timezone ووحدة واضحتين.
- الخطوط العربية تُراجع للوضوح والأوزان والتشكيل، مع fallback محلي آمن.
- التصميم يتحمل text expansion ولا يعتمد على عرض ثابت للنص الإنجليزي.

اللغات الأخرى وسياسة locale fallback: `NOT_DECIDED`.

## 8. الوصول (Accessibility)

الهدف المقترح للواجهة العامة هو **WCAG 2.2 AA**، لكنه `PROPOSED` وليس شهادة
مطابقة حتى التدقيق اليدوي والآلي.

### 8.1 البنية الدلالية

- عناصر HTML الأصلية أولًا: `button` و`input` و`label` و`nav` بدل div تفاعلي.
- كل control له accessible name وحالة disabled/expanded/pressed صحيحة.
- ترتيب DOM يطابق ترتيب القراءة والتركيز.
- ARIA يضيف معنى عند غياب عنصر أصلي مناسب، ولا يصلح HTML غير صحيح.
- اللغة الأساسية وأجزاء اللغة المختلفة معلّمة بـ`lang`.

### 8.2 لوحة المفاتيح والتركيز

- كل فعل قابل بلوحة المفاتيح دون trap.
- focus indicator واضح في الوضعين ولا يُزال لمجرد الشكل.
- ترتيب Tab منطقي؛ لا positive `tabindex`.
- عند ظهور خطأ، ينتقل التركيز فقط إذا كان ذلك يساعد ولا يفقد سياق المستخدم.
- modal مستقبلي يحتاج focus trap صحيحًا وإرجاع التركيز للعنصر الذي فتحه.
- skip link للمحتوى إذا أصبح التنقل المتكرر عائقًا.

### 8.3 الإدراك البصري والحركي

- contrast للنص والعناصر والحالات يحقق الهدف المعتمد.
- اللون ليس الإشارة الوحيدة للنجاح أو الخطأ أو عدم التوفر.
- مساحة لمس لا تقل عن هدف WCAG 2.2 المناسب، مع تباعد يمنع اللمس الخاطئ.
- تدعم الواجهة تكبير 200% وإعادة تدفق حتى عرض CSS مكافئ لـ320px دون فقد وظيفة.
- احترام `prefers-reduced-motion` وإيقاف الحركات غير الضرورية.
- لا flashing أو animation يعرقل القراءة.
- zoom لا يُعطل عبر viewport meta.

### 8.4 الرسائل الديناميكية

- `aria-live="polite"` للحالات غير العاجلة، و`assertive` نادرًا للأخطاء التي تحتاج
  تدخلًا فوريًا.
- لا يعاد نطق الرد كاملًا مع كل token إذا أضيف streaming لاحقًا؛ يلزم تجميع مناسب.
- حالة busy مرتبطة بالمنطقة الصحيحة ولا تجعل الصفحة كلها غير قابلة للوصول.
- أخطاء الحقول مرتبطة بـ`aria-describedby` وتبقى مرئية نصيًا.

## 9. التصميم المتجاوب

### 9.1 Mobile-first

- يبدأ التخطيط من عرض صغير ثم يضيف المساحة بالـmedia/container queries عند الحاجة.
- breakpoints تتبع انهيار المحتوى لا أسماء أجهزة بعينها.
- لا horizontal scroll للصفحة عند 320 CSS px، مع استثناء محتوى مثل code block داخل
  حاوية قابلة للتمرير وموسومة.
- الوحدات المرنة (`rem`, `%`, `minmax`, `clamp`) مفضلة على أبعاد ثابتة عمياء.
- الصور والوسائط لا تتجاوز الحاوية، ولها أبعاد لتقليل layout shift.
- safe-area insets تؤخذ بالحسبان للأجهزة ذات الحواف عند وجود عناصر مثبتة.

### 9.2 مكوّنات الدردشة

- composer يبقى قابلًا للوصول عند ظهور لوحة مفاتيح الهاتف دون تغطية الرسالة أو زر
  الإرسال.
- لا يعتمد الارتفاع على `100vh` فقط؛ تُقيم dynamic viewport units مع fallback.
- الرسائل الطويلة وURLs والكود تلتف أو تتمرر داخل حدودها دون توسيع الصفحة.
- أزرار النسخ/إعادة المحاولة لا تظهر بالـhover فقط.
- auto-scroll يحدث فقط إذا كان المستخدم قرب النهاية؛ لا يسحب قارئًا رجع لأعلى.
- موضع scroll يُحفظ عند إضافة محتوى سابق مستقبلًا.
- typing/loading indicator لا يسبب layout shift متكررًا.

### 9.3 أحجام الاختبار المرشحة

لا تحل قائمة أجهزة محل الاختبار المرن، لكن الحد الأدنى يشمل:

- 320px و360px و390px للهواتف.
- 768px للأجهزة اللوحية/التكبير.
- 1024px و1440px لسطح المكتب.
- landscape قصير الارتفاع.
- 200% zoom وtext-only zoom حيث يدعمه المتصفح.
- RTL وLTR في كل فئة.

Browser/device support matrix النهائي: `NOT_DECIDED`.

## 10. الأداء الإدراكي وأداء الواجهة

الأداء جزء من UX، لكن budgets تحتاج baseline فعليًا. المقاييس المرشحة:

- LCP وINP وCLS وفق Web Vitals على أجهزة وشبكات ممثلة.
- زمن إتاحة composer والتفاعل الأول.
- زمن ظهور حالة submitting بعد الفعل.
- حجم CSS/JS والخطوط وعدد الطلبات.
- زمن استجابة التطبيق منفصلًا عن مزود النموذج.

القواعد:

- تحديث بصري فوري بعد الإرسال دون الادعاء بالنجاح.
- لا blocking script غير ضروري في المسار الأساسي.
- تحميل الخطوط لا يخفي النص؛ fallback مناسب وتقليل الأوزان.
- lazy loading للمحتوى غير الحرج فقط، وليس التحكم الأساسي.
- skeleton يستخدم عندما يعكس بنية معروفة؛ spinner مناسب للانتظار القصير.
- لا prefetch لبيانات حساسة أو مكلفة بلا نية واضحة.

Performance budgets والقيم المستهدفة: `NOT_MEASURED` حتى تشغيل قياسات ممثلة.

## 11. الشبكات البطيئة والانقطاع

- الكشف عن `navigator.onLine` إشارة فقط وليس إثبات اتصال.
- فشل الشبكة يعرض رسالة قابلة للاستعادة ولا يمحو الإدخال.
- retry يدوي افتراضي للطلبات المكلفة أو غير idempotent.
- الطلب الجاري له timeout معلوم وحالة بعد انتهائه.
- offline mode ليس منفذًا ولا يُعلن عنه.
- لا service worker أو cache للمحادثات قبل سياسة بيانات وإبطال واضحة.
- إن استعيد draft محليًا مستقبلًا، يلزم موافقة وتصنيف ومدة وحذف وتشفير مناسب؛ لا
  `localStorage` افتراضيًا للمحتوى الحساس.

## 12. الثقة والخصوصية في التجربة

- يظهر بوضوح متى تُرسل البيانات إلى Backend أو مزود خارجي.
- جمع أقل قدر من البيانات، ولا dark patterns للموافقة أو الاحتفاظ.
- خيار عدم الحفظ لا يكون أقل وضوحًا من خيار الحفظ.
- الحذف يشرح النطاق والمهلة والاستثناءات القانونية عند تنفيذ التخزين.
- لا prompt أو رد أو بريد أو token في analytics افتراضيًا.
- telemetry اختيارها وإخفاء الهوية والاحتفاظ بها تحتاج مراجعة خصوصية.
- رسائل MFA والجلسة والصلاحية لا تكشف وجود حساب لشخص آخر.

## 13. التحليلات وقياس UX

لا تُجمع analytics قبل تحديد غرض قانوني وتقني. القياسات المقترحة، عند الموافقة:

- task completion ووقت المهمة الأساسية.
- validation error rate وduplicate attempts.
- abandon rate أثناء الانتظار، مفصولًا حسب فئة الخطأ.
- تغيير اللغة ونجاح الحالة بعده دون ربط غير ضروري بالهوية.
- استخدام لوحة المفاتيح/اللمس بصورة مجمعة لا fingerprinting.
- user-reported ease ورضا نوعي، لا نسب مُختلقة.

تمنع event payloads المحتوى الحر والرسائل والأسرار. خطة analytics والموافقة والاحتفاظ:
`NOT_DECIDED`.

## 14. البحث واختبار قابلية الاستخدام

قبل تغييرات كبيرة:

1. تحديد المهمة والفرضية ومعيار النجاح.
2. استخدام prototype أو بيئة لا تحتوي بيانات حساسة.
3. إشراك مستخدمين يمثلون العربية والإنجليزية والهاتف ولوحة المفاتيح/قارئ الشاشة
   بقدر النطاق.
4. مراقبة إتمام المهمة والأخطاء والتردد دون توجيه المستخدم للحل.
5. تصنيف النتائج حسب الشدة والتكرار والأثر، لا التفضيل البصري فقط.
6. إعادة الاختبار بعد الإصلاح.

عدد المشاركين وخطة البحث والتعويض والموافقة: `NOT_DECIDED`. لا يوصف التصميم بأنه
“بديهي” قبل اختبار مستخدمين فعليين.

## 15. الاختبارات الآلية واليدوية

### اختبارات آلية

- تطابق مفاتيح i18n العربية والإنجليزية.
- صدق حالات القدرات وتعطيل العناصر غير المنفذة.
- keyboard events مع IME ومنع الإرسال المكرر.
- DOM semantics والأسماء والحالات الأساسية.
- contrast وaxe-equivalent scan كإشارة أولية عند اعتماد أداة.
- visual regression لأحجام مختارة بعد تثبيت baseline ومراجعة الفروق.
- responsive overflow واختفاء controls الأساسية.
- عدم فقد draft عند أخطاء الشبكة ضمن السياسة المعتمدة.

### اختبارات يدوية

- لوحة مفاتيح فقط في RTL وLTR.
- قارئا شاشة على الأقل يمثلان المتصفحات المستهدفة عند اعتماد support matrix.
- zoom/reflow وhigh contrast وreduced motion.
- هاتف فعلي بلوحة مفاتيح عربية وإنجليزية، portrait وlandscape.
- شبكة بطيئة وانقطاع وtimeout و429 وprovider failure.
- قراءة نص طويل وكود وURL ومحتوى bidirectional.

الأتمتة لا تثبت المطابقة لـWCAG أو سهولة الاستخدام. نتائج accessibility audit وuser
study الحالية: `NOT_PERFORMED`.

## 16. Design Tokens والمكونات

يمكن توحيد القيم الحالية تدريجيًا عبر CSS custom properties:

- ألوان semantic مثل text/surface/border/success/warning/error/focus.
- typography scale وline-height تدعمان العربية والإنجليزية.
- spacing/radius/shadow/motion durations.
- z-index layers محدودة وموثقة.

كل مكوّن موحد يحتاج حالات idle/hover/focus/disabled/loading/error وRTL وreduced
motion. لا تُنشأ مكتبة مكونات مستقلة أو Storybook قبل أن يثبت التكرار والحاجة؛
حالتها `DEFERRED`.

## 17. إدارة التغيير

- تغييرات الواجهة في دفعات صغيرة منفصلة عن آلية النشر والمزامنة.
- لقطة أو وصف قبل/بعد مع قائمة الأحجام واللغات المختبرة.
- لا تغيير مرئي واسع دون مراجعة عربية/إنجليزية وإمكانية وصول.
- bug قابل للتكرار يضاف له اختبار regression حيث يمكن.
- feature flag لا يتجاوز صدق الحالة أو الأمن، وله مالك وتاريخ إزالة.
- rollback لا يفقد بيانات مستخدم أو يحول Backend حقيقيًا إلى Demo صامت.

## 19. بوابات الإطلاق

### مسموح الآن

- إصلاحات صغيرة للوصول والاستجابة مع اختبارات regression.
- اختبار أحجام الشاشة واللغتين محليًا ببيانات غير حساسة.
- تحسين رسائل الخطأ مع الحفاظ على العقود والصدق.
- توحيد CSS tokens تدريجيًا دون إعادة كتابة.

### مانع لادعاء جاهزية UX العامة

- لا بحث مستخدمين أو task-based usability test موثق.
- لا accessibility audit ولا إثبات WCAG 2.2 AA.
- لا browser/device matrix معتمدة.
- لا baseline للأداء أو اختبارات شبكة ممثلة.
- حالات timeout/cancel/rate limit تحتاج تحققًا من طرف إلى طرف.
- بوابات الهوية والأمن والموثوقية والنشر العام ما زالت مفتوحة.

### شرط تغيير الحالة

لا تصبح UX `APPROVED` بمجرد أن تبدو الواجهة جيدة على شاشة واحدة. يلزم نجاح مهام
محددة لمستخدمين ممثلين، مراجعة RTL/LTR، اختبار لوحة المفاتيح وقارئ الشاشة والتكبير،
تحقق responsive على مصفوفة معتمدة، وقياسات أداء وحالات فشل موثقة.
