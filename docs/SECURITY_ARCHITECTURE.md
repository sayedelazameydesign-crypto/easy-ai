# Cela.sh — Security Architecture Baseline

> **الحالة:** مسودة أمنية للمراجعة البشرية؛ ليست شهادة امتثال ولا دليلًا على تنفيذ
> الضوابط.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** متطلبات الأمان قبل أي إتاحة عامة للـBackend أو نظام الأدوات.

## 1. القرار المعماري

الأمان في Cela.sh طبقات متقاطعة، وليس ميزة يضيفها ناقل أو مزود واحد. الأولويات:

1. حماية هوية المستخدم والمفاتيح والبيانات أثناء النقل والتخزين.
2. منع اتساع صلاحيات الوكيل أو الأداة عن صلاحيات المستدعي.
3. منع الاستهلاك غير المحدود لمزود النموذج.
4. اكتشاف الثغرات ومعالجتها عبر دورة تطوير قابلة للقياس.
5. تحديد الالتزامات القانونية الفعلية قبل جمع بيانات شخصية أو صحية.

هذه الوثيقة لا تعتمد مزودًا أو منصة أو نظام هوية. كل قرار غير محسوم يبقى
`NOT_DECIDED`، ولا يبدأ النشر العام قبل إغلاق الموانع المحددة أدناه.

## 2. حدود الثقة والأصول الحساسة

### الأصول التي يجب حمايتها

- مفاتيح مزود النموذج ومفاتيح التشفير وأسرار الجلسات.
- حسابات المستخدمين وعوامل MFA ورموز الاستعادة.
- محتوى المحادثات والملفات والموافقات وسجل الأدوات.
- بيانات المزامنة الخام والمنقحة ونسخ vault المشفرة.
- سجلات التدقيق وحدود الحصة والتكلفة.
- إعدادات الاستضافة وCI/CD وسلسلة التوريد البرمجية.

### حدود الثقة

- المتصفح والـwebhooks والمدخلات الخارجية غير موثوقة.
- الشبكة الداخلية و`localhost` لا يمنحان الثقة تلقائيًا.
- مزود النموذج والاستضافة أطراف خارجية تخضع لعقود وسياسات بيانات مستقلة.
- الأداة المحلية لا ترث كامل بيئة الوكيل أو نظام الملفات.
- GitHub Actions ومخزن الأسرار حدود تشغيل حساسة تحتاج أقل صلاحية.

## 3. تشفير البيانات أثناء النقل

### المتطلبات

- HTTPS إلزامي لكل اتصال عام، مع **TLS 1.3 مفضلًا** وTLS 1.2 كحد أدنى فقط عند
  الحاجة إلى توافق موثق. تُعطل الإصدارات والباقات الضعيفة.
- شهادة صالحة وسلسلة ثقة صحيحة وتجديد آلي ومراقبة انتهاء الصلاحية.
- HSTS بعد التأكد من أن كل النطاقات الفرعية المقصودة تدعم HTTPS، مع مراجعة قرار
  `includeSubDomains` وpreload قبل تفعيله.
- لا mixed content ولا downgrade صامت إلى HTTP.
- اتصال الـBackend بالمزود يتحقق من الشهادة واسم المضيف، ولا يسمح بتعطيل التحقق.
- service-to-service يستخدم TLS وهوية خدمة مستقلة؛ يُقيّم mTLS فقط عند وجود عدة
  خدمات وبنية شهادات تبرر التعقيد.
- SSH/SFTP، إن اعتمدا لاحقًا، يحتاجان host-key pinning وخوارزميات حديثة؛ لا يقبل
  `StrictHostKeyChecking=no`.

### إدارة الترويسات والجلسات

- Cookies، إن استُخدمت، تكون `Secure` و`HttpOnly` و`SameSite` مناسبًا للنموذج.
- رموز المصادقة لا توضع في URL أو query string أو logs.
- CORS قائمة أصول دقيقة وليس وسيلة مصادقة.
- توضع سياسة CSP مناسبة للواجهة في دفعة مستقلة قبل النشر العام.

### السلوك عند الفشل

فشل TLS أو التحقق من الشهادة يمنع الاتصال؛ لا fallback إلى اتصال غير مشفر. يظهر
خطأ آمن ولا تُعرض تفاصيل الشهادة الداخلية للمستخدم.

## 4. تشفير البيانات أثناء التخزين

### البيانات المخزنة

قبل تخزين أي فئة يجب توثيق الغرض والمالك والمدة والحذف. الفئات منفصلة:

- حالة جلسة قصيرة العمر.
- محتوى محادثة اختياري بموافقة المستخدم.
- سجل تشغيل منقح.
- سجل تدقيق.
- بيانات خام مشفرة في vault المحلي.

### المتطلبات

- استخدام تشفير المنصة المُدار للقرص وقاعدة البيانات والنسخ الاحتياطية، مع توثيق
  الخوارزمية وحدود الحماية. عبارة “encrypted at rest” وحدها لا تحمي من حساب خدمة
  مخترق يملك صلاحية فك التشفير.
- للحقول شديدة الحساسية: envelope encryption بمفتاح بيانات ومفتاح رئيسي في
  KMS/HSM مُدار إن بررت البيانات ذلك.
- AES-256-GCM أو خوارزمية AEAD معيارية مدعومة بالمكتبة المعتمدة؛ لا تشفير مخصص.
- nonce فريد لكل عملية AEAD، مع authentication tag والتحقق قبل فك المحتوى.
- كلمات المرور لا تُشفّر لاستعادتها؛ تُشتق باستخدام Argon2id بإعدادات معتمدة وقت
  التنفيذ، أو خدمة هوية مُدارة لا تعطي التطبيق كلمة المرور أصلًا.
- عوامل MFA والرموز الاحتياطية تُعامل كأسرار، وتُخزن بصيغة غير قابلة للاسترجاع حيث
  يسمح البروتوكول.
- النسخ الاحتياطية مشفرة، محدودة الوصول، ولها اختبارات استعادة وحذف.
- لا يعتمد التخزين الدائم على ذاكرة العملية أو filesystem مؤقت للاستضافة.

## 5. إدارة المفاتيح والأسرار

- الأسرار في secret manager أو GitHub Secrets حسب بيئة التشغيل؛ لا تدخل Git أو
  HTML أو JavaScript أو صور الحاويات أو logs.
- مفاتيح منفصلة للتطوير والاختبار والإنتاج، ولمزود/بيئة/غرض مختلف.
- أقل صلاحية لكل secret، مع rotation وجدول انتهاء وإبطال فوري عند الاشتباه.
- التطبيق لا يطبع كائن config قد يحتوي الأسرار، ولا يعيد جسم خطأ المزود.
- يمنع وصول pull requests غير الموثوقة إلى أسرار الإنتاج.
- لا يمر مفتاح مزود النموذج إلى المتصفح أو أداة محلية لا تحتاجه.
- تُسجل عمليات إدارة المفتاح كأحداث تدقيق دون تسجيل قيمة المفتاح.

### قرارات غير محسومة

- مزود KMS/secret manager يتبع منصة الاستضافة: `NOT_DECIDED`.
- مدة rotation وملاك المفاتيح وإجراء الاسترداد: `NOT_DECIDED`.
- الحاجة إلى customer-managed keys أو HSM: `NOT_DECIDED` حسب تصنيف البيانات.

## 6. الهوية والوصول (IAM)

### المصادقة

قبل API عامة يجب اعتماد أحد الخيارات:

- مزود هوية مُدار يدعم OIDC/OAuth 2.1 وجلسات آمنة.
- جلسات خادمية قصيرة العمر مع حماية CSRF مناسبة.
- tokens قصيرة العمر مع issuer/audience/signature/expiry والتحقق من replay حيث يلزم.

لا يُبتكر بروتوكول مصادقة خاص.

### MFA

- MFA إلزامي للحسابات الإدارية ومشغلي الإنتاج.
- WebAuthn/passkeys أو مفاتيح FIDO2 مفضلة لمقاومة التصيد.
- TOTP خيار احتياطي؛ SMS ليس عاملًا مفضلًا للعمليات الحساسة.
- رموز الاستعادة أحادية الاستخدام، مخزنة بصورة آمنة، وتدويرها حدث تدقيق.
- step-up authentication مطلوب لتغيير الأسرار أو الصلاحيات أو الفوترة أو تعطيل
  ضوابط التكلفة.

### التفويض

يستخدم النموذج المفاهيمي:

```text
Permission = (tenant, capability, operation, resource)
EffectivePermissions = Caller ∩ Agent ∩ ConnectorPolicy
```

السياسة:

- deny-by-default.
- المنع الصريح له أولوية.
- RBAC للأدوار المستقرة مثل user/operator/security-admin.
- قيود resource وtenant وملكية البيانات تطبق فوق RBAC؛ يمكن استخدام ABAC عند
  وجود حاجة مثبتة، لا كقواعد متناثرة غير قابلة للمراجعة.
- فصل واجبات: من يغيّر حدود الإنفاق أو الأسرار لا يعتمد تدقيقه منفردًا للعمليات
  شديدة الحساسية.
- مراجعة دورية للحسابات الخاملة والصلاحيات المرتفعة وحسابات الخدمة.
- لا تمنح الأداة صلاحية أعلى من الوكيل أو المستخدم المستدعي.

### الجلسات والإبطال

- مدة قصيرة مناسبة، rotation بعد تسجيل الدخول أو رفع الصلاحية.
- إبطال عند تغيير كلمة المرور أو MFA أو الاشتباه أو إنهاء الحساب.
- لا تستخدم `request_id` أو `task_id` أو IP كإثبات هوية.

## 7. حماية API والاستهلاك

- تحقق schema وأنواع وحدود كل طلب قبل الاتصال بالمزود.
- حدود مستقلة لحجم الجسم والرسالة والسجل والمخرجات والمهلة.
- rate limit موزع لكل مستخدم/tenant؛ IP إشارة إضافية فقط.
- سياسة trusted proxies محددة حسب الاستضافة؛ لا ثقة عشوائية في forwarded headers.
- quota يومية/شهرية وحد concurrent requests.
- provider token limit ليس حدًا ماليًا.
- budget alert ليس hard stop.
- hard spending cap أو prepaid بلا auto-recharge إن أمكن، إضافة إلى kill switch
  داخل البوابة ومراقبة الاستهلاك.
- عند نفاد الحصة أو فشل المزود: خطأ صريح، دون رد تجريبي يوحي بالنجاح.
- عناوين الاتصال الخارجي ثابتة أو allowlisted؛ أي وجهة ديناميكية مستقبلية تحتاج
  حماية SSRF/DNS rebinding وإعادة تحقق بعد redirects.

## 8. التسجيل والتدقيق والخصوصية

### التسجيل التشخيصي

يسمح بمعرف الطلب وحالة عامة وزمن وحجوم تقريبية. يمنع افتراضيًا:

- كلمات المرور والمفاتيح وAuthorization وCookies.
- prompts والردود والملفات.
- بيانات شخصية مباشرة.
- stack traces في رد العميل.

### سجل التدقيق

يسجل من قام بماذا وعلى أي مورد والنتيجة والموافقة ومعرف الطلب. يحتاج:

- وصول قراءة محدود.
- مدة احتفاظ معتمدة.
- حماية من العبث إذا تطلب التهديد ذلك.
- تنبيه على تغيير الأدوار والأسرار وMFA والفوترة والـkill switch.

### الخصوصية

- data minimization وpurpose limitation.
- موافقة مستقلة لحفظ المحادثة؛ عدم الخلط بينها وبين logs.
- حذف وتصدير وتصحيح البيانات وفق الالتزام القانوني المعتمد.
- عدم إرسال PII أو أسرار إلى Gemini Unpaid أو أي tier لا تسمح سياسته بذلك.
- لا تستخدم بيانات المستخدم لتقييم أو تدريب داخلي دون موافقة وسياسة معلنة.

## 9. إدارة الثغرات والاختبارات الأمنية

### في كل تغيير

- مراجعة شيفرة أمنية للتغييرات الحساسة.
- اختبارات وحدة للحالات السلبية وحدود المخططات والأخطاء الآمنة.
- فحص أسرار يمنع القيم الفعلية في Git وartifacts.
- SAST وفحص dependencies وlockfiles عند إدخال نظام حزم مناسب.
- pinning لإصدارات Actions والاعتماديات وفق سياسة مراجعة وتحديث.
- SBOM وartifact provenance عند الانتقال إلى بناء Backend منشور.

### دوريًا

- تحديثات أمنية وفق شدة الثغرة وSLA معتمد.
- DAST على بيئة اختبار مصرح بها فقط.
- فحص إعدادات السحابة وIAM والأسرار وTLS والترويسات.
- مراجعة threat model بعد مزود أو ناقل أو أداة جديدة.
- اختبار استعادة النسخ الاحتياطية وخطة الاستجابة للحوادث.

### اختبار اختراق

- قبل أول إطلاق عام وبعد تغييرات معمارية كبيرة، بواسطة طرف مخول وبنطاق مكتوب.
- يغطي المصادقة والتفويض وعزل tenant وAPI abuse وSSRF وحقن prompts والأدوات
  ورفع الملفات وإدارة الجلسات وسلسلة التوريد.
- يحظر الاختبار غير المصرح لخدمات المزود أو الاستضافة.
- تُصنف النتائج، ويحدد مالك وموعد إصلاح، ثم retest لإغلاقها.
- اختبار الاختراق لقطة زمنية ولا يحل محل secure SDLC.

### SLA أولي يحتاج اعتمادًا

| الشدة | الإجراء المقترح | الحالة |
|---|---|---|
| حرجة مستغلة أو تسريب سر | احتواء فوري، إبطال الأسرار وتقييم إيقاف الخدمة | `NOT_DECIDED` |
| حرجة | إصلاح عاجل ضمن SLA بشري معتمد | `NOT_DECIDED` |
| عالية/متوسطة/منخفضة | جداول حسب المخاطر والتعرض | `NOT_DECIDED` |

لا تعتمد مدد رقمية قبل تحديد فريق التشغيل والتزاماته.

## 10. الاستجابة للحوادث والاستمرارية

يجب قبل الإنتاج تحديد:

1. قنوات الإبلاغ والتصعيد والمسؤول المناوب.
2. playbooks لتسريب مفتاح، اختراق حساب، إنفاق غير طبيعي، وتسريب بيانات.
3. kill switch للمزود والموصلات الخارجية.
4. rotation وإبطال sessions/tokens والمفاتيح.
5. حفظ أدلة منقحة وسجل زمني للحادث.
6. تقييم الإخطار القانوني والمستخدمين حسب الاختصاص.
7. post-incident review وإجراءات تمنع التكرار.

النسخ الاحتياطي لا يساوي الاستمرارية؛ يجب تعريف RPO/RTO واختبار الاستعادة بعد
اختيار مخزن دائم. التشغيل المحلي يبقى البديل الآمن إن لم تعتمد حماية عامة كافية.

## 11. الامتثال

الامتثال يعتمد على نوع البيانات والمستخدمين والغرض والمناطق، ولا يجوز ادعاء أن
Cela.sh “متوافق” لمجرد استخدام تشفير أو مزود يحمل شهادة.

### GDPR

يُقيّم عند معالجة بيانات أشخاص في الاتحاد الأوروبي/المنطقة الاقتصادية الأوروبية
أو استهدافهم. يحتاج تحديد controller/processor، الأساس القانوني، حقوق صاحب البيانات،
DPA، سجلات المعالجة، نقل البيانات الدولي، retention وDPIA عند ارتفاع المخاطر.

### HIPAA

ينطبق فقط عند معالجة PHI ضمن علاقة covered entity/business associate في الولايات
المتحدة. يتطلب BAA مع كل مزود ذي صلة وضوابط إدارية ومادية وتقنية. الخطط المجانية
لا تُفترض مؤهلة، ولا تُرسل PHI قبل اعتماد قانوني وتعاقدي مكتوب.

### مصر والقوانين المحلية

يجب تقييم قانون حماية البيانات الشخصية المصري رقم 151 لسنة 2020 وأي لوائح أو
متطلبات نقل عبر الحدود تنطبق على صاحب المشروع والمستخدمين. هذه الوثيقة ليست رأيًا
قانونيًا؛ يلزم مختص قانوني عند جمع بيانات شخصية أو إطلاق خدمة عامة.

### معايير طوعية محتملة

يمكن استخدام OWASP ASVS وOWASP API Security Top 10 كخط أساس تقني. ISO 27001 أو
SOC 2 برامج حوكمة وتدقيق مؤسسية وليست خصائص مكتبة، ولا يُدعى الحصول عليها دون
نطاق وتدقيق وشهادة فعلية.

## 12. بوابات الإطلاق

### يسمح بالتطوير المحلي فقط عندما

- لا أسرار في Git أو المتصفح.
- البيانات الاختبارية غير شخصية وغير سرية.
- Backend مربوط بـloopback أو بيئة معزولة.
- المزود غير متصل، أو الاتصال مصرح ومقيد صراحة.

### يمنع النشر العام حتى إغلاق الموانع

| المانع | الحالة |
|---|---|
| مزود/model/tier وسياسة بيانات معتمدة | `NOT_DECIDED` |
| منصة استضافة وsecret manager وTLS | `NOT_DECIDED` |
| نظام هوية ومصادقة وMFA للإدارة | `NOT_DECIDED` |
| RBAC/resource/tenant enforcement | `NOT_DECIDED` |
| rate limit موزع وquota لكل مستخدم | `NOT_DECIDED` |
| hard cost control وkill switch مختبران | `NOT_DECIDED` |
| retention/deletion/consent للمحادثات | `NOT_DECIDED` |
| incident response ومالكو التشغيل | `NOT_DECIDED` |
| تقييم قانوني لنطاق GDPR/HIPAA/القانون المحلي | `NEEDS_VALIDATION` |
| مراجعة أمنية واختبار اختراق قبل الإطلاق | `NOT_DECIDED` |

## 13. سجل القرارات البشرية

| القرار | الخيارات الأولية | الأثر | الحالة |
|---|---|---|---|
| مزود الهوية | OIDC مُدار؛ جلسات خادمية | الأمان والتكلفة والتشغيل | `NOT_DECIDED` |
| MFA | WebAuthn أساسي؛ TOTP احتياطي | مقاومة التصيد والاسترداد | `NOT_DECIDED` |
| KMS/secret manager | تابع للاستضافة؛ حل مُدار مستقل | إدارة المفاتيح والتكلفة | `NOT_DECIDED` |
| تشفير الحقول | تشفير المنصة فقط؛ envelope encryption للحقول | حماية البيانات وتعقيد الإدارة | `NOT_DECIDED` |
| الاحتفاظ بالمحادثات | بلا حفظ؛ opt-in بمدة محددة | الخصوصية وتجربة المستخدم | `NOT_DECIDED` |
| الامتثال المطلوب | لا بيانات منظمة؛ GDPR؛ HIPAA؛ محلي | العقود والاستضافة والعمليات | `NEEDS_VALIDATION` |
| اختبار الاختراق | داخلي؛ طرف مستقل | التكلفة والاستقلالية والنطاق | `NOT_DECIDED` |
| SLA الثغرات | حسب شدة ومخاطر | قدرة الفريق والاستمرارية | `NOT_DECIDED` |

لا ينتقل قرار إلى `APPROVED` دون صاحب قرار وتاريخ ودليل واعتماد بشري.

## 14. التوصية الحالية

- لا نشر عام ولا ناقل جديد.
- التشغيل المحلي هو الافتراضي المؤقت.
- استكمال قرارات المزود والاستضافة والهوية وسياسة البيانات أولًا.
