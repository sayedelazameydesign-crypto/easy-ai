# Cela.sh — Sustainability & Cost Efficiency Baseline

> **الحالة:** مسودة معمارية للمراجعة البشرية؛ ليست تقرير انبعاثات ولا دليلًا على
> تحقيق وفر مالي أو بيئي.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** كفاءة موارد التطبيق والنموذج والتخزين والبنية التشغيلية، وإدارة
> التكاليف، دون اعتماد مزود أو منصة أو خطة مدفوعة.

## 1. القرار المعماري

تُعامل الاستدامة كجزء من كفاءة النظام وإدارة الطلب، لا كادعاء تسويقي. ترتيب القرار:

1. تجنب العمل والبيانات غير الضرورية.
2. قياس الموارد والتكلفة لكل نتيجة مفيدة.
3. اختيار أبسط بنية وأصغر مورد يحقق SLO والأمن.
4. تحسين الشيفرة والاستعلامات والحمولات قبل إضافة موارد.
5. استخدام التوسع المرن ضمن حدود مالية وتشغيلية.
6. تقييم الأثر البيئي بمصادر ومنهجية معلنة دون دقة زائفة.

لا يوجد حاليًا قياس طاقة أو انبعاثات أو تكلفة إنتاج فعلية. كل قيمة مستهدفة تبقى
`NOT_MEASURED` أو `NOT_DECIDED` حتى اختيار المنصة والمزود وتشغيل حمل ممثل.

## 2. الحدود والمقاييس

### 2.1 حدود النظام

أي تقييم يجب أن يوضح ما يشمله:

- متصفح المستخدم ونقل الشبكة، إذا توفرت بيانات موثوقة.
- Backend وload balancer والتخزين والنسخ الاحتياطي والمراقبة.
- مزود النموذج، بما يشمل input/output tokens والميزات الإضافية.
- CI/CD والاختبارات وartifact storage.
- مزامنة Google Drive الحالية ضمن حدودها الفعلية.
- بيئات التطوير والاختبار والإنتاج كل على حدة.

لا تُجمع أرقام من حدود مختلفة في نسبة واحدة دون بيان المنهجية.

### 2.2 مؤشرات الكفاءة

مقاييس مرشحة:

- CPU-seconds وmemory working set لكل طلب ناجح.
- زمن instance وعدد replicas ومتوسط/ذروة utilization.
- bytes المنقولة والمخزنة لكل مستخدم نشط أو عملية.
- database queries والصفوف المقروءة لكل operation.
- tokens المدخلة والمخرجة والمحاولات لكل نتيجة ناجحة.
- cache hit ratio عند وجود cache مبرر.
- تكلفة كل طلب ناجح وكل ألف طلب وكل tenant وفترة.
- تكلفة idle مقابل تكلفة الحمل الفعلي.
- نسبة الفشل وretry والعمل الملغى أو المكرر.
- نمو التخزين والنسخ والسجلات ومعدل الحذف.

المقام يجب أن يمثل قيمة مفيدة مثل “طلب ناجح ضمن SLO”، لا عدد requests خام يمكن
زيادته بالـretries.

### 2.3 الطاقة والانبعاثات

إذا قيس الأثر البيئي لاحقًا يجب فصل:

- قياس طاقة مباشر إن وفرته المنصة.
- تقدير من استخدام CPU/GPU والمدة ومعاملات منشورة.
- market-based وlocation-based emissions عند توفرهما.
- operational emissions عن embodied emissions إن شملتها المنهجية.

مصادر عوامل الانبعاث، المنطقة، الفترة، PUE، عدم اليقين وما لا يشمله القياس يجب أن
تُنشر مع النتيجة. لا تُحوّل التكلفة إلى CO2e بمعامل اعتباطي، ولا يُقال “محايد
كربونيًا” أو “أخضر” دون تحقق مستقل مناسب.

## 3. كفاءة معمارية

- يبقى modular monolith نقطة البداية لتقليل overhead الشبكة والتشغيلية.
- لا microservices أو broker أو cache موزع أو cluster قبل حاجة وقياس.
- التطبيق عديم الحالة قدر الإمكان لتسهيل right-sizing وإزالة النسخ الخاملة.
- العمل الخلفي، إن ظهر، يُجمع ويُجدول فقط إذا لم يضر SLO أو الخصوصية.
- لا polling متكرر عندما تكفي إشارة موجودة؛ ولا اتصال دائم دون حاجة مثبتة.
- لكل dependency قيمة تشغيلية واضحة وسياسة إزالة إذا لم تعد مستخدمة.
- بيئات غير الإنتاج لها جدول إيقاف أو scale-to-zero عندما يكون آمنًا ومسموحًا.

البساطة لا تتجاوز الأمن أو الموثوقية: لا إيقاف لنسخة لازمة لـSLO، ولا حذف backup
أو log قبل مدة الاحتفاظ، ولا نقل لمنطقة أقل انبعاثًا يخالف سيادة البيانات.

## 4. كفاءة الحوسبة والذاكرة

### 4.1 CPU

- profiling قبل التحسين؛ لا يُستنتج الاختناق من الانطباع.
- تجنب parsing/serialization والتحويلات المتكررة في المسار الساخن.
- bounded concurrency يمنع context switching وانهيار الموارد.
- خوارزميات وهياكل بيانات تناسب الحجم الفعلي، مع benchmarks للتغيير المؤثر.
- compression يُفعل وفق حجم الحمولة وتكلفة CPU، لا افتراضيًا لكل استجابة صغيرة.
- لا busy waiting أو loops بلا backoff.

### 4.2 الذاكرة

- streaming للملفات الكبيرة فقط بعد اعتماد الحاجة والعقد؛ لا تحميل غير محدود للذاكرة.
- حدود واضحة للـbody والرسائل والسجل والـqueues والـcaches.
- cache له maximum size وTTL وسياسة eviction وقياس فائدة.
- لا احتفاظ بمحتوى المحادثة في process بعد انتهاء الحاجة.
- soak tests تكشف leaks ونمو الذاكرة والتراكم.
- worker count يوازن CPU والذاكرة واتصالات التخزين بدل مضاعفة عمياء.

### 4.3 Right-sizing

- اختيار instance size من قياسات p95 مع headroom معتمد.
- مراجعة requested مقابل used resources دوريًا.
- التوسع الرأسي أو الأفقي يراعي نقطة كفاءة التكلفة، وليس utilization وحده.
- min/max replicas يمنعان idle غير المبرر والتكلفة غير المحدودة.
- cold start مقبول في التطوير إذا وُثق، لكنه لا يُفرض على SLO عام دون قرار.

قيم utilization/headroom وحجم instance: `NOT_DECIDED`.

## 5. كفاءة استخدام النموذج

تكلفة النموذج وموارده قد تفوق Backend، لذلك:

- تحديد أقصى input/output tokens لكل operation.
- عدم إرسال كامل سجل المحادثة افتراضيًا؛ اختيار أقل سياق يحقق المهمة.
- إزالة التكرار والبيانات غير اللازمة قبل الإرسال دون تغيير المعنى أو الخصوصية.
- عدم طلب عدة نتائج أو reasoning/ميزات مرتفعة التكلفة بلا حاجة منتج.
- اختيار أصغر نموذج يحقق معيار جودة معتمد؛ لا اختيار الأرخص على حساب سلامة المهمة.
- قياس الجودة والتكلفة والـlatency معًا على evaluation set غير حساس.
- retry يستهلك tokens وتكلفة ويخضع لميزانية محددة.
- caching لنتائج النموذج يحتاج تطابقًا دلاليًا وخصوصية وretention؛ ليس افتراضيًا.
- batching يُقيّم فقط للمهام غير التفاعلية التي تسمح مهلاتها وسياسة بياناتها بذلك.

لا يُعتمد مزود أو نموذج أو طبقة مجانية نهائيًا بهذه الوثيقة. جودة النموذج مقابل
التكلفة والطاقة: `NOT_EVALUATED`.

## 6. كفاءة الشبكة والواجهة

- تقليل JavaScript/CSS والخطوط والطلبات غير الحرجة دون framework غير لازم.
- compression وcaching headers للأصول الثابتة مع content hashes عند توفر pipeline.
- عدم تحميل صور أو خطوط أو ترجمات غير مطلوبة للمهمة الأولى.
- responsive images وformats مناسبة إذا أضيفت وسائط فعلية.
- pagination وحدود للاستجابات؛ لا نقل مجموعات كاملة افتراضيًا.
- عدم polling لحالة لا تتغير كثيرًا؛ cadence يخضع للحاجة والتكلفة.
- metrics/traces sampling مضبوط، ولا إرسال bodies أو بيانات حساسة.

Performance budget للواجهة وحجم النقل: `NOT_MEASURED` وفق `UX_ARCHITECTURE.md`.

## 7. كفاءة التخزين ودورة حياة البيانات

- عدم حفظ المحادثات افتراضيًا دون غرض وموافقة وسياسة حذف.
- فصل بيانات الجلسة والمحادثة والتدقيق والتشغيل ولكل منها retention مستقل.
- ضغط أو أرشفة البيانات القديمة فقط إذا بقيت مطلوبة ويمكن استعادتها ضمن RTO.
- حذف caches وartifacts والنسخ المؤقتة تلقائيًا حسب lifecycle policy.
- logs بمستوى مناسب وsampling؛ لا debug دائم في الإنتاج.
- indexes مبررة بالاستعلامات وتكلفة الكتابة والتخزين.
- النسخ الاحتياطي يشمل البيانات المطلوبة فقط مع retention يوازن RPO والقانون.
- deduplication يُستخدم عندما يثبت وفورات دون تعقيد أو تسريب عبر tenants.

الحذف المستدام لا يتجاوز legal hold أو الاستجابة للحوادث. Retention الفعلي لكل فئة:
`NOT_DECIDED`.

## 8. CI/CD وبيئات التطوير

- تشغيل jobs اللازمة فقط حسب الملفات المتغيرة مع بقاء البوابات الأمنية الملزمة.
- caching للتبعيات بمفاتيح صحيحة، ولا cache لأسرار أو artifacts غير موثوقة.
- cancel-in-progress للتغييرات المتجاوزة عندما لا يلزم حفظ نتيجة قديمة.
- timeouts لكل job لمنع موارد عالقة.
- عدم تكرار build نفسه في عدة jobs إذا أمكن مشاركة artifact متحقق منه بأمان.
- retention قصير معقول للartifacts غير المطلوبة قانونيًا أو تشغيليًا.
- scheduled jobs لها غرض ومالك ومؤشر استخدام؛ تُزال إذا لم تعد مفيدة.
- runners ذاتية الاستضافة لا تُضاف إلا إذا بررت كلفتها وأمنها وتشغيلها.

لا تُضعف بوابة scan أو الاختبارات لتقليل دقائق CI. الكفاءة تحذف العمل المكرر لا
التحقق الضروري.

## 9. المرونة السحابية والاستدامة

عند اختيار منصة:

- تقييم regions المتاحة وسكن البيانات وlatency والطاقة ومصادر الانبعاث المنشورة.
- تفضيل خدمات مُدارة فقط عندما يقلل مجموع العبء والموارد والمخاطر؛ “managed” لا
  يعني تلقائيًا أقل تكلفة أو أثرًا.
- autoscaling يعتمد حملًا مفيدًا وحدود DB والمزود، مع سقف مالي.
- scale-to-zero للبيئات غير الحرجة إذا لم يسبب فقد بيانات أو كسر اختبارات/مهام.
- scheduled scaling بعد إثبات نمط، وpredictive scaling بعد بيانات كافية.
- spot/preemptible للمهام القابلة للاستئناف فقط، لا للمسار الحرج دون تعافٍ.
- commitments/reservations بعد baseline ثابت، لا قبل فهم الاستخدام.

لا تُختار منطقة على الكربون وحده إذا زادت retries أو latency أو خرقت الخصوصية أو
قللت التوافر. منصة الاستضافة والمنطقة: `NOT_DECIDED`.

## 10. إدارة التكاليف (FinOps)

### 10.1 تخصيص ورؤية التكلفة

- فصل حسابات/مشاريع وبيئات التطوير والاختبار والإنتاج عند اختيار المنصة.
- tags/labels إلزامية: environment، service، owner، cost-center أو بديل معتمد.
- تكلفة مزود النموذج تُنسب إلى operation وtenant ضمن ضوابط الخصوصية.
- dashboard يوضح actual وforecast وunit cost وidle cost وأكبر drivers.
- reconciliation دوري بين قياسات التطبيق وفاتورة المزود دون تسجيل prompts.
- التكاليف المشتركة لها قاعدة توزيع موثقة، ولا تُخفى في “miscellaneous”.

### 10.2 الميزانيات والحدود

- budget شهري لكل بيئة وخدمة مع thresholds تدريجية.
- التنبيه المبكر ليس hard cap؛ يجب توثيق الفرق.
- hard spending cap أو prepaid محدود لمزود النموذج عندما تسمح الخدمة.
- auto-recharge معطل افتراضيًا أو محدود بموافقة بشرية إن توفر.
- kill switch يوقف العمليات المكلفة مع إبقاء وظائف الإدارة والتشخيص الآمنة.
- quotas لكل مستخدم/tenant/operation تمنع مستهلكًا واحدًا من استنزاف الميزانية.
- anomaly detection يراعي الزيادة الطبيعية ولا ينفذ حذفًا/إيقافًا خطرًا أعمى.

قيم الميزانية ومن يوافق على التجاوز ومسار التصعيد: `NOT_DECIDED`.

### 10.3 التوقع والقرار

كل ميزة تشغيلية جديدة تحتاج تقديرًا يوضح:

- الطلب المتوقع والسيناريو المنخفض/المرجح/المرتفع.
- تكلفة ثابتة ومتغيرة ومرة واحدة.
- أثر tokens والتخزين والنقل والمراقبة والدعم والنسخ الاحتياطي.
- تكلفة الفشل والـretries والاحتفاظ، لا happy path فقط.
- حساسية السعر وحدود الخطة ومخاطر تغير التسعير.
- معيار إيقاف التجربة إذا لم تحقق قيمة أو تجاوزت التكلفة.

الأسعار يعاد التحقق منها من المصادر الرسمية وقت القرار؛ لا تعتمد أرقام تاريخية في
وثيقة ثابتة كحقيقة دائمة.

## 11. الحماية من الهدر والإساءة

- authentication قبل أي استخدام مكلف عام.
- rate limiting وحصة موزعة وحدود concurrency.
- أقصى tokens وحجم ومدد لكل طلب.
- منع duplicate submission وreplay عبر idempotency عند الحاجة.
- validation مبكر قبل استدعاء المزود أو التخزين المكلف.
- SSRF ورفع الملفات محكومان بالحجم والنوع والوجهة.
- circuit breaker وretry budget يمنعان تضخيم عطل خارجي.
- تنبيه على تغير unit cost و429 وretries وعدد requests لكل هوية.
- الحسابات الإدارية محمية بـMFA ولا تمتلك كل خدمة صلاحية فوترة.

خفض التكلفة لا يبرر إخفاء خطأ أو الرد بنتيجة Demo عند فشل الخدمة الحقيقية.

## 12. المشتريات ودورة الحياة

- تقييم lock-in وتكلفة الخروج ونقل البيانات قبل اعتماد خدمة.
- توثيق حدود الخطة المجانية والنوم والحصة والتخزين والانتهاء، ولا اعتبارها SLA.
- لا وسيلة دفع أو خطة مدفوعة دون تفويض صريح وميزانية ومالك.
- مراجعة تراخيص التبعيات ودعمها الأمني وعمرها؛ dependency مهجورة لها خطة استبدال.
- حذف موارد التجارب والبيئات المؤقتة وsnapshots غير المطلوبة عبر عملية مراجعة آمنة.
- infrastructure inventory وملاك الموارد شرط قبل إنتاج متعدد الخدمات.

إعادة استخدام جهاز أو خدمة قائمة لا يتجاوز العزل والأمن وSLO.

## 13. المفاضلات

تُسجل المفاضلة صراحة، ومنها:

- **الكفاءة مقابل التوافر:** replica إضافية قد تزيد الطاقة والتكلفة لكنها لازمة لـSLO.
- **الضغط مقابل CPU:** تقليل الشبكة قد يزيد الحوسبة.
- **cache مقابل الذاكرة والخصوصية:** hit rate يجب أن يبرر التخزين والمخاطر.
- **نموذج أصغر مقابل الجودة:** لا وفر مقبول إذا فشلت المهمة أو زادت الإعادات.
- **منطقة منخفضة الانبعاث مقابل latency/سيادة البيانات:** القانون والأمن أولًا.
- **احتفاظ أقصر مقابل التحقيق/الاستعادة:** يحدد وفق الغرض والقانون وRPO.
- **scale-to-zero مقابل cold start:** يختلف بين التطوير والإنتاج.

أي قرار يضر هدفًا إلزاميًا يحتاج قبول مخاطر ومالكًا وموعد مراجعة.

## 14. الاختبار والتحقق

قبل ادعاء تحسن كفاءة:

- benchmark قابل للتكرار قبل/بعد على نفس البيئة والحمل.
- قياس CPU والذاكرة والزمن والطلبات والتكلفة، لا latency وحده.
- load/soak tests لكشف leaks وتغير unit cost عند التوسع.
- اختبار حد tokens والحصة وhard cap وkill switch.
- اختبار autoscaling يثبت عدم توسيع اختناق 429 أو DB.
- اختبار lifecycle والحذف دون حذف backups أو سجلات لازمة.
- مقارنة جودة للنموذج عند تقليل السياق أو تغيير النموذج.
- تسجيل عدم اليقين والفروق الإحصائية وتغيرات البيئة.

الاختبارات لا تتصل بمزود حقيقي دون تصريح ومفتاح وحد مالي. mocks لا تثبت فاتورة أو
طاقة منصة حقيقية. حالة baseline الحالية: `NOT_MEASURED`.

## 15. الرصد والمراجعة

Dashboard الاستدامة/التكلفة المقترح:

- طلبات ناجحة وفاشلة وملغاة وretries.
- unit cost واتجاهه حسب operation والبيئة.
- tokens input/output ونسبة السياق غير المستخدم إن أمكن قياسها بأمان.
- CPU/memory/storage/network utilization والنمو.
- idle resources وreplicas عند الحد الأدنى/الأقصى.
- عمر البيانات والنسخ والartifacts مقابل retention.
- budget actual/forecast وanomalies والإجراءات المتخذة.
- energy/carbon estimates فقط مع مصدر ومنهجية وعدم يقين.

مراجعة شهرية مقترحة للتكلفة والسعة، وربع سنوية للعمارة ودورة الحياة. cadence
والمالكون الفعليون: `NOT_DECIDED`.

| retention حسب فئة البيانات | `NOT_DECIDED` | غرض وقانون وRPO وتحقيق |
| نموذج/مزود أكثر كفاءة | `NOT_EVALUATED` | جودة وتكلفة وlatency وبيانات |
| cache موزع | `NOT_APPROVED` | hit rate مثبت وخصوصية وتكلفة |
| scale-to-zero للإنتاج | `NOT_APPROVED` | SLO وcold-start وموثوقية |
| قياس CO2e | `NOT_IMPLEMENTED` | مصدر بيانات ومنهجية وحدود وعدم يقين |
| ادعاء استدامة عام | `BLOCKED` | قياس قابل للتدقيق ومراجعة قانونية |
| الجاهزية التشغيلية | `BLOCKED` | إغلاق بوابات القسم التالي |

## 17. بوابات الإطلاق

### مسموح الآن

- profiling وbenchmarks محلية ببيانات غير حساسة.
- إزالة عمل مكرر مثبت مع اختبارات regression.
- إضافة حدود موارد وتكلفة محلية fail-closed.
- توثيق مفاضلات ومصادر أسعار دون اعتماد مزود.

### مانع للإطلاق العام

- لا workload/capacity/cost baseline معتمد.
- لا مصادقة أو حصة موزعة أو hard cost cap أو kill switch مثبت.
- لا ميزانية أو ملاك أو مسار تصعيد للإنفاق.
- لا retention/lifecycle policy معتمدة للبيانات والسجلات والنسخ.
- لا load/soak/autoscaling tests ممثلة.
- منصة الاستضافة والمزود والمنطقة ما زالت غير محسومة.
- بوابات الأمن والموثوقية والتوسع ما زالت مفتوحة.

### شرط تغيير الحالة

لا تصبح الاستدامة `APPROVED` بمجرد خفض فاتورة أو حذف موارد. يلزم baseline موثق،
مقياس قيمة ووحدة، اختبار قبل/بعد، تحقق أن SLO والأمن والجودة لم تتراجع، واعتماد
ميزانية وحدود تشغيل. أي ادعاء بيئي يحتاج منهجية ومصدرًا وعدم يقين ومراجعة مناسبة.
