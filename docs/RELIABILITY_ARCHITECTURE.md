# Cela.sh — Reliability & Availability Architecture Baseline

> **الحالة:** مسودة معمارية للمراجعة البشرية؛ ليست دليلًا على تنفيذ التوافر العالي
> أو نجاح النسخ الاحتياطي أو التعافي من الكوارث.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** متطلبات الموثوقية قبل إتاحة الـBackend أو نظام الأدوات للعامة.

## 1. القرار المعماري

الموثوقية خاصية قابلة للقياس وليست اسم خدمة أو وعدًا مطلقًا. لا تعتمد هذه الوثيقة
مزود استضافة أو قاعدة بيانات أو منطقة جغرافية. يبقى التشغيل المحلي هو الوضع المؤقت،
ويبقى النشر العام `BLOCKED` حتى تُعتمد أهداف الخدمة وتُختبر إجراءات الاستعادة.

الأولويات بالترتيب:

1. سلامة البيانات ومنع الازدواج أو الأثر الخارجي غير المقصود.
2. فشل محدود وصريح بدل انتشار العطل أو نجاح زائف.
3. استعادة قابلة للاختبار من نسخ مستقلة.
4. توافر يتناسب مع SLO وحجم الاستخدام، لا تعقيد احترازي غير مبرر.
5. ضبط التكلفة؛ لا تتحول آليات إعادة المحاولة أو التكرار إلى استهلاك غير محدود.

لا يعني توثيق load balancer أو replica أو backup أنها موجودة حاليًا.

## 2. المصطلحات ومقاييس الخدمة

- **SLI:** قياس فعلي مثل نسبة الطلبات الناجحة ضمن زمن محدد.
- **SLO:** هدف داخلي قابل للقياس خلال نافذة زمنية.
- **SLA:** التزام تعاقدي؛ لا يُعلن قبل اعتماد قانوني وتشغيلي.
- **RTO:** أقصى زمن مستهدف لاستعادة خدمة بعد كارثة.
- **RPO:** أقصى مقدار زمني مقبول لفقد البيانات.
- **Error budget:** مقدار الإخفاق المسموح به وفق SLO.

قبل الإنتاج يجب تحديد SLIs منفصلة على الأقل لـ:

- توافر نقطة الصحة ونقاط API الأساسية.
- نجاح الطلبات من طرف التطبيق، مع فصل أخطاء العميل عن أخطاء النظام.
- زمن الاستجابة p50 وp95 وp99 بحسب العملية.
- نجاح استدعاء المزود وزمنه، منفصلًا عن توافر التطبيق.
- حداثة البيانات، نجاح النسخ الاحتياطي، ونجاح اختبارات الاستعادة.
- نسبة العمليات المعلقة أو الملغاة أو المكررة.

قيم SLO وRTO وRPO الحالية: `NOT_DECIDED`. لا يجوز اختراع نسبة مثل 99.9% قبل
معرفة المنصة والتكلفة وحساسية البيانات وساعات الدعم.

## 3. نموذج الفشل

يجب أن يغطي التصميم والاختبار حالات الفشل الآتية:

- تعطل process أو instance أو نفاد الذاكرة أو القرص.
- انقطاع الشبكة، DNS، TLS، أو انتهاء شهادة.
- بطء مزود النموذج، 429، 5xx، أو انقطاعه الكامل.
- تعطل قاعدة البيانات أو فقد الاتصال أو فساد عملية migration.
- تلف بيانات أو حذف بشري أو اختراق حساب إداري.
- فشل منطقة الاستضافة أو تعذر حساب المزود كله.
- خطأ نشر، إعداد غير صالح، أو secret منتهي/مُبطل.
- ازدواج webhook أو إعادة محاولة طلب ذي أثر خارجي.
- نفاد الحصة أو بلوغ hard cost cap.

لكل اعتماد خارجي يجب تسجيل: المالك، المهلة، سياسة retry، السلوك المتدهور، حدود
التكلفة، وطريقة العزل. تعطل مزود النموذج لا يتحول إلى رد ثابت يوصف بأنه نجاح.

## 4. تحمل الأخطاء

### 4.1 عزل الفشل

- تفصل حدود واضحة بين الواجهة والـBackend ومزود النموذج والتخزين والموصلات.
- تستخدم timeouts نهائية لكل اتصال؛ لا طلب ينتظر بلا حد.
- يمر الإلغاء حتى الطبقة التي تستطيع إيقاف العمل، مع تجاهل النتيجة المتأخرة بأمان.
- تحدد concurrency وqueue depth لكل عملية؛ لا queue غير محدودة في الذاكرة.
- circuit breaker مشروط بقياسات فعلية، وله half-open probes وحدود واضحة؛ لا يُضاف
  قبل فهم سلوك الاعتماد.
- bulkheads أو pools منفصلة للعمليات الثقيلة عند ثبوت التنافس على الموارد.
- health checks لا تعتمد على مورد مكلف ولا تعرض أسرارًا.

### 4.2 إعادة المحاولة والـbackoff

- retry فقط للأخطاء المؤقتة المعروفة، وليس validation أو authentication أو quota
  الصلبة أو العمليات غير الآمنة.
- exponential backoff مع jitter وعدد محاولات ومدة كلية محددين.
- احترام `Retry-After` ضمن deadline وحد التكلفة.
- منع retry storms عبر ميزانية محاولات مشتركة وconcurrency limits.
- كل محاولة تستهلك من حصة الطلب والـtokens والتكلفة؛ لا retry مجاني منطقيًا.

### 4.3 idempotency واتساق الأثر

- GET والقراءات لا تُحدث أثرًا جانبيًا.
- العمليات القابلة للتكرار تستخدم idempotency key مرتبطًا بالهوية والعملية والموارد
  ومدة احتفاظ محددة.
- لا يُعاد إرسال عملية كتابة غير idempotent تلقائيًا بعد نتيجة مجهولة.
- لا ادعاء exactly-once؛ النمط الواقعي at-least-once مع deduplication أو مصالحة.
- العمليات متعددة الأنظمة توثق نقطة commit وكيفية التعويض أو الإصلاح اليدوي.

### 4.4 السلوك المتدهور

عند فشل المزود أو التخزين:

- تعرض حالة صريحة قابلة للتشخيص مع `request_id` منقح.
- يمكن إبقاء الواجهة والمحتوى الثابت متاحين، لكن لا يوصف ذلك بتوافر وظيفة AI.
- لا fallback لمزود ثانٍ دون قرار معماري وسياسة بيانات وتكلفة منفصلين.
- لا حفظ للمحادثة إذا لم يؤكد التخزين نجاحه.
- تُوقف الأدوات ذات الأثر الخارجي إذا تعذر التحقق من الهوية أو الصلاحية أو التدقيق.

## 5. التوافر العالي

التوافر العالي قرار لاحق لا شرطًا تلقائيًا لكل بيئة. قبل اعتماده يجب إثبات أن SLO
لا يمكن تحقيقه ببنية أبسط.

### الحد الأدنى المرشح للإنتاج العام

- نسخ تطبيق عديمة الحالة قدر الإمكان، خلف load balancer مُدار.
- readiness تمنع توجيه المرور قبل الجاهزية، وliveness لا تسبب restart loop.
- rolling أو blue/green deployment مع إيقاف آمن للطلبات الجارية.
- تخزين دائم مُدار لا يعتمد على filesystem مؤقت للـinstance.
- توزيع النسخ على failure domains عند دعم المنصة، مع إثبات لا مجرد إعداد اسمي.
- autoscaling محدود بسقف موارد وتكلفة، ولا يعتمد على CPU وحده للمهام البطيئة.
- session state خارج process أو جلسات موقعة قصيرة العمر بحسب نموذج الهوية.

### التكرار والاتساق

- تُوثق دلالات replica: synchronous أو asynchronous، واحتمال stale reads وفقد
  الكتابات عند failover.
- لا يُقرأ سجل الصلاحيات أو الحصة أو idempotency من replica متأخرة إذا أدى ذلك
  إلى تجاوز أمني أو مالي.
- promotion/failover له مالك وإجراء واختبار؛ وجود replica لا يثبت إمكانية التعافي.
- active-active متعدد المناطق مؤجل ما لم يفرضه SLO؛ يزيد تعقيد الاتساق والتكلفة.

### الاعتماديات ذات النقطة الواحدة

قبل الإطلاق تُعد قائمة Single Points of Failure تشمل DNS والشهادات والهوية وقاعدة
البيانات وsecret manager وCI/CD ومزود النموذج. كل نقطة إما تُكرر، أو لها استعادة
موثقة، أو تُقبل مخاطرتها صراحة بمالك وموعد مراجعة.

## 6. النسخ الاحتياطي والاستعادة

### النطاق والسياسة

يجب حصر البيانات القابلة للنسخ قبل اختيار الجدول:

- قاعدة البيانات الدائمة ومخططها وmigration metadata.
- إعدادات لازمة لإعادة البناء، مع بقاء الأسرار في مخزن أسرار منفصل.
- سجلات التدقيق حسب سياسة الاحتفاظ.
- بيانات المستخدم التي وافق على حفظها فقط.
- لا تُنسخ caches أو بيانات مشتقة يمكن إعادة بنائها دون مبرر.

السياسة تعتمد RPO وتصنيف البيانات. الحد الأدنى:

- نسخ آلية مجدولة مع مراقبة النجاح والفشل.
- تشفير أثناء النقل والتخزين ومفاتيح منفصلة وفق خط الأساس الأمني.
- نسخة مستقلة منطقيًا عن الحساب أو الصلاحيات التشغيلية الأساسية لمقاومة الحذف
  والـransomware، مع immutability إن كانت المنصة تدعمها.
- retention متدرج وحذف منضبط يراعي طلبات الحذف والالتزامات القانونية.
- checksums أو تحقق سلامة، وفهرس يوضح الوقت والمصدر والمخطط.
- least privilege: التطبيق لا يملك حذف كل النسخ الاحتياطية.
- مراقبة السعة وعمر آخر نسخة ناجحة.

يمكن تقييم نمط 3-2-1 للبيانات الحرجة، لكنه ليس ادعاء تنفيذ ولا قاعدة عمياء؛ يلزم
تحديد ما إذا كانت النسخ عبر وسيط أو مزود مستقل مطلوبة ومسموحة قانونيًا.

### اختبار الاستعادة

نجاح job النسخ لا يساوي backup صالحًا. يجب:

1. استعادة دورية في بيئة معزولة غير إنتاجية.
2. التحقق من فك التشفير والمخطط وعدد السجلات وعينات سلامة منقحة.
3. تشغيل smoke tests دون إرسال بيانات حقيقية إلى مزود خارجي.
4. قياس RPO/RTO الفعليين ومقارنتهما بالهدف.
5. توثيق النتيجة والفشل والإجراء التصحيحي دون نسخ أسرار أو بيانات شخصية للسجل.
6. التخلص الآمن من بيئة الاختبار بعد الانتهاء.

تواتر النسخ والاحتفاظ واختبار الاستعادة: `NOT_DECIDED` حتى تصنيف البيانات واختيار
التخزين. لا توجد نتيجة اختبار استعادة حالية.

## 7. التعافي من الكوارث

### سيناريوهات الخطة

Runbooks منفصلة على الأقل لـ:

- rollback لنشر معيب أو migration فاشلة.
- استعادة قاعدة البيانات إلى نقطة زمنية معتمدة.
- فقد منطقة أو حساب استضافة.
- فقد/اختراق مفاتيح أو secret manager.
- حذف أو فساد واسع للبيانات.
- تعطل مزود النموذج لفترة ممتدة.
- اختراق أمني يتطلب العزل قبل الاستعادة.

### محتوى كل runbook

- شروط الإعلان عن الحادث وشدته وصاحب القرار.
- أدوار incident commander والاتصال والتقنية والخصوصية.
- خطوات العزل والحفظ الجنائي دون تعطيل متطلبات الإبلاغ.
- ترتيب استعادة الهوية والمفاتيح والتخزين والتطبيق ثم الاتصالات الخارجية.
- قرار failover أو restore، وشروط الرجوع إلى المنطقة الأساسية.
- تحقق وظيفي وأمني قبل فتح المرور.
- قناة اتصال بديلة إذا تعطلت المنصة الأساسية.
- سجل زمني، post-incident review، وإجراءات متابعة بمالك وموعد.

### استراتيجية الموقع البديل

- backup-and-restore أو pilot light أو warm standby أو active-active: `NOT_DECIDED`.
- يُختار النمط وفق RTO/RPO والتكلفة وسيادة البيانات، لا وفق اسم تسويقي.
- لا يُفترض أن منطقة ثانية تحمي من خطأ منطقي أو credential مخترق.
- لا cross-region replication قبل مراجعة نقل البيانات والخصوصية.

تُجرى tabletop exercise قبل الإطلاق العام، ثم تمرين استعادة تقني وفق جدول معتمد.
لا يوصف DR بأنه جاهز حتى ينجح تمرين موثق ضمن الأهداف.

## 8. الرصد والتنبيه

### القياسات

- معدل الطلبات والنجاح والفشل والمهلات حسب operation، دون أبعاد عالية الكثافة.
- latency percentiles وqueue depth وsaturation وrestarts.
- dependency errors و429 وcircuit state والمحاولات الإضافية.
- database connections وreplication lag وسعة التخزين.
- عمر آخر backup ناجح ونتيجة آخر restore drill.
- استهلاك tokens والتكلفة والحصة وبلوغ hard cap.

### السجلات والتتبع

- correlation/request IDs مولدة في الحد الموثوق ولا تمنح صلاحية.
- structured logs منقحة وفق `SECURITY_ARCHITECTURE.md`.
- trace sampling مضبوط؛ لا prompts أو أسرار أو بيانات شخصية افتراضيًا.
- مراقبة مستقلة قدر الإمكان كي لا تختفي مع الخدمة نفسها.

### التنبيه

- alert على أعراض تؤثر في المستخدم أو تهدد RPO/RTO، لا على كل spike عابر.
- لكل alert مالك وrunbook وشدة وقناة تصعيد.
- تختبر مسارات التنبيه دوريًا، وتراجع التنبيهات المزعجة أو الصامتة.
- لا ادعاء 24/7 support قبل تعيين مناوبة فعلية وموافقة بشرية.

## 9. النشر والتغيير الآمن

- builds قابلة للتكرار، migrations مراجعَة، ونسخ قاعدة البيانات قبل تغييرات خطرة
  عندما تثبت الحاجة.
- backward-compatible expand/migrate/contract للتغييرات التي تعبر نسخًا متعددة.
- rollback artifact معروف؛ لا يُفترض أن rollback الشيفرة يعكس migration تلقائيًا.
- canary أو staged rollout عند دعم المنصة وحجم المرور، مع توقف آلي مضبوط لا أعمى.
- feature flags لها مالك وتاريخ إزالة ولا تتجاوز المصادقة أو بوابة الأمان.
- error budget يوقف تغييرات الميزات غير الضرورية عندما تتدهور الخدمة.
- chaos testing يبدأ في بيئة معزولة وبفرضية ونطاق أمان؛ لا يُجرى على الإنتاج دون
  موافقة وخطة إيقاف.

## 10. الاختبار والتحقق

قبل النشر العام يلزم دليل على:

- unit/integration tests للمهل والإلغاء وretry وidempotency والسلوك المتدهور.
- load test بمعدل واقعي وحدود تكلفة، لا هجوم غير مصرح على المزود.
- soak test لاكتشاف التسرب والتراكم.
- فشل instance أثناء طلبات جارية دون فساد أو ازدواج أثر.
- تعطل dependency وDNS وTLS و429 و5xx والبطء الجزئي.
- استعادة backup ضمن RPO/RTO المعتمدين.
- rollback للنشر وmigration وفق runbook.
- tabletop وتمرين DR موثقين.

غياب اختبار أو تعذره يعني `NOT_TESTED`، وليس نجاحًا. نتائج mock تثبت عقد التطبيق
فقط ولا تثبت سلوك مزود أو منصة حقيقية.

## 11. ملكية التشغيل وسجل القرار

| القرار | الحالة | المطلوب للحسم |
|---|---|---|
| منصة الاستضافة وfailure domains | `NOT_DECIDED` | تحقق رسمي وتجربة حساب فعلية |
| SLO/SLI ونافذة القياس | `NOT_DECIDED` | توقعات المنتج وساعات الدعم والميزانية |
| RTO/RPO حسب فئة البيانات | `NOT_DECIDED` | تصنيف البيانات وتحليل أثر الأعمال |
| تخزين دائم وجدول النسخ | `NOT_DECIDED` | اختيار التخزين وسياسة الاحتفاظ |
| استراتيجية DR | `NOT_DECIDED` | RTO/RPO والتكلفة وسيادة البيانات |
| عدد النسخ وautoscaling | `NOT_DECIDED` | load test وSLO وحد التكلفة |
| نموذج المناوبة والتصعيد | `NOT_DECIDED` | تعيين ملاك فعليين |
| مزود نموذج احتياطي | `NOT_APPROVED` | حاجة مثبتة ومراجعة بيانات وتكلفة منفصلة |
| readiness للإطلاق العام | `BLOCKED` | إغلاق بوابات القسم التالي |

أي قبول مخاطر يحتاج وصف الخطر والأثر والمالك وتاريخ الانتهاء والمراجع البشري.

## 12. بوابات الإطلاق

### مسموح الآن

- تطوير محلي ببيانات اختبار غير حساسة.
- اختبارات unit وintegration محلية لا تتصل بمزود حقيقي.
- إعداد runbooks وقوالب قياس دون الادعاء بتشغيلها.

### مانع للإطلاق العام

- عدم اعتماد SLO وRTO وRPO ومالكي التشغيل.
- عدم اختيار منصة وتخزين دائم وفهم failure domains.
- عدم وجود مصادقة وحصص موزعة وحد تكلفة وفق الخط الأساس الأمني.
- عدم وجود نسخ آلي مشفر ومراقب واختبار استعادة ناجح.
- عدم اختبار rollback وfailover والسلوك عند فشل الاعتماديات.
- عدم وجود مراقبة وتنبيه وrunbooks ومسار تصعيد فعلي.
- عدم إغلاق متطلبات الأمن والخصوصية واختبار الاختراق.

### شرط تغيير الحالة

لا تتحول الحالة إلى `APPROVED` بمجرد إعداد configuration أو وثيقة. يلزم دليل اختبار
مؤرخ، ملاك مسمون خارج المستودع عند الحاجة، قبول مخاطر متبقية، وموافقة بشرية على
SLO والتكلفة والاستجابة للحوادث.

## 13. العلاقة مع الوثائق الأخرى

- `AI_BACKEND_DESIGN.md`: المزود والاستضافة والحصة والتكلفة.
- `COMMUNICATION_ARCHITECTURE.md`: المهلة والإلغاء والأخطاء ودلالات النقل.
- `SECURITY_ARCHITECTURE.md`: IAM والتشفير والتسجيل والاستجابة للحوادث والامتثال.

عند التعارض تُختار القاعدة الأكثر تحفظًا إلى أن يُسجل قرار بشري. لا تعدل هذه الوثيقة
بنية `sync/` أو عقود التخزين الحالية، ولا تعتمد ناقلًا أو مزودًا أو خدمة جديدة.
