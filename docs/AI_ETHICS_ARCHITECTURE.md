# Cela.sh — AI Ethics, Transparency & Accountability Baseline

> **الحالة:** مسودة حوكمة للمراجعة البشرية؛ ليست شهادة عدالة أو تفسيرًا لآلية نموذج
> خارجي أو موافقة على استخدامات طبية أو قانونية أو عالية الأثر.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** العدالة والشفافية والتفسير والمساءلة والخصوصية لكل قدرة تستخدم نموذجًا
> أو نظام قرار آلي مستقبلًا.

## 1. القرار الحاكم

يظل Cela.sh واجهة Demo صريحة أو Backend اختياريًا محدودًا حتى اعتماد مزود وهوية
وسياسة بيانات وتقييمات مناسبة. لا توجد حاليًا موافقة على قرارات آلية عالية الأثر،
ولا على تدريب نموذج أو fine-tuning أو استخدام محادثات المستخدم للتحسين.

المبادئ الحاكمة:

1. لا يُفوّض قرار يمس حقًا أو خدمة أساسية أو سلامة إنسان إلى النموذج وحده.
2. العدالة تُعرّف وتقاس حسب use case؛ لا يمكن ضمان انعدام الانحياز عمومًا.
3. الشفافية تصف القدرات والحدود والبيانات والمسؤولية بصدق.
4. التفسير يوضح الأدلة والعوامل والقواعد المطبقة، ولا يدعي كشف “تفكير داخلي” غير
   متاح أو موثوق.
5. المسؤولية تبقى لدى أشخاص وجهات محددين؛ النموذج ليس صاحب مسؤولية قانونية.
6. الخصوصية وتقليل البيانات شرط مسبق، لا مفاضلة اختيارية لرفع الدقة.
7. عند عدم كفاية الأدلة أو الضوابط يكون السلوك رفضًا أو تصعيدًا، لا ثقة مصطنعة.

حالة الاستخدامات الحساسة والعالية الأثر: `PROHIBITED_PENDING_REVIEW`.

## 2. نطاق النظام والجهات المتأثرة

أي تقييم أخلاقي يجب أن يشمل دورة الحياة كاملة:

- من يحدد الغرض ومقاييس النجاح.
- من يوفر النموذج أو البيانات أو المعرفة المسترجعة.
- من يطور الواجهة والـBackend والسياسات.
- المستخدم المباشر والشخص الذي قد يتأثر دون أن يكون مستخدمًا.
- المراجع البشري أو صاحب القرار النهائي.
- مشغلو الاستضافة والمراقبة والدعم والحوادث.

الجهات المتأثرة قد تشمل أفرادًا ذُكرت بياناتهم في prompt أو ملف دون أن يوافقوا على
الاستخدام. لا يكفي اعتبار المستخدم وحده stakeholder.

## 3. تصنيف الاستخدام والمخاطر

قبل تفعيل أي قدرة يُسجل use-case card يتضمن الغرض والمستخدمين والأثر والبيانات
والبدائل. التصنيف المقترح:

### مخاطر منخفضة

- صياغة أو تلخيص محتوى غير حساس مع مراجعة المستخدم.
- أفكار إبداعية لا تقدم كحقيقة أو قرار.
- مساعدة تقنية ضمن حدود واضحة واختبار مستقل للمخرجات.

لا تعني “منخفضة” عدم الحاجة إلى الخصوصية والأمن والشفافية.

### مخاطر متوسطة

- توصيات تؤثر في قرارات عمل أو تعليم أو مالية غير ملزمة.
- معالجة مستندات داخلية أو بيانات شخصية محدودة.
- أتمتة قد تسبب خسارة وقت أو تكلفة أو سمعة إذا أخطأت.

تحتاج مراجعة بشرية وضوابط استخدام ومراقبة وrollback.

### مخاطر عالية/حساسة

- تشخيص أو علاج أو فرز طبي.
- رأي أو استراتيجية قانونية مخصصة أو قرار قضائي.
- ائتمان وتأمين وتوظيف وترقية وفصل وتعليم وقبول وإسكان.
- هوية بيومترية أو مراقبة أو profiling حساس.
- أهلية لخدمة عامة أو قرار يمس حقًا قانونيًا.
- إجراءات ذاتية خارجية يصعب عكسها.

هذه الاستخدامات **غير معتمدة**. تحتاج تقييمًا قانونيًا وحقوقيًا وأمنيًا مستقلًا،
خبراء مجال، human decision authority، تحققًا سريريًا/مهنيًا عند الانطباق، وآلية
اعتراض. عبارة “ليس نصيحة” وحدها لا تجعلها آمنة.

## 4. حالات الاستخدام المحظورة افتراضيًا

حتى قرار ومراجعة صريحة، يُحظر:

- قرار نهائي آلي في مجال عالي الأثر.
- استنتاج صفات حساسة أو سرية من نص أو صورة دون ضرورة وأساس قانوني.
- تصنيف الأشخاص حسب العرق أو الدين أو الصحة أو التوجه أو الرأي السياسي أو سمات
  محمية لاتخاذ قرار ضدهم.
- social scoring أو ترتيب جدارة بشرية عام.
- خداع المستخدم بشأن كونه يتفاعل مع AI أو بشأن مصدر الإجابة.
- انتحال شخص حقيقي أو إنشاء دليل مزور أو تضليل متعمد.
- مراقبة خفية أو جمع بيانات زائد عن الغرض.
- تدريب على محادثات المستخدم أو بيانات `sync/` أو `vault/` تلقائيًا.
- أداة ذاتية بصلاحيات مفتوحة أو أثر خارجي بلا موافقة وتفويض وحدود.
- ادعاء دقة أو حياد أو تفسير أو امتثال غير مقاس.

أي استثناء يحتاج مالكًا وأساسًا قانونيًا وتحليل ضرر وموافقة بشرية موثقة ومدة مراجعة.

## 5. العدالة والإنصاف

### 5.1 تعريف العدالة

لا يوجد metric واحد يضمن العدالة، وقد تتعارض المقاييس. لكل use case يجب تحديد:

- القرار أو المساعدة التي ينتجها النظام.
- من يستفيد ومن يتحمل الخطأ.
- أنواع الضرر: حرمان، جودة أقل، إساءة تمثيل، تخصيص موارد، أو عبء إضافي.
- الفئات المحمية والمتأثرة وفق القانون والسياق.
- نوع الخطأ الأخطر: false positive أو false negative أو تفاوت الجودة.
- المقياس المختار وسبب ملاءمته والآثار التي لا يقيسها.

Fairness definition وprotected slices الحالية: `NOT_DEFINED` لأنه لا يوجد use case
عالي الأثر معتمد.

### 5.2 مصادر الانحياز

- تحيز المصدر والتغطية واللغة واللهجة والزمن.
- أخطاء labels واختلاف annotators.
- historical bias داخل “ground truth”.
- proxy variables التي تعيد بناء سمة حساسة.
- تصميم المهمة أو الهدف أو threshold.
- تفاوت جودة الواجهة والوصول والأجهزة.
- feedback loops التي تزيد ظهور مجموعة وتخفي أخرى.
- اختلاف جودة المزود أو safety filters عبر اللغات.
- deployment context مختلف عن بيانات التقييم.

### 5.3 القياس

وفق الحاجة والمشروعية:

- أداء كلي وأداء كل شريحة مع confidence intervals وحجم العينة.
- false positive/negative وcalibration وabstention حسب الشريحة.
- worst-group performance والفئات التقاطعية عندما تسمح الخصوصية والحجم.
- جودة العربية الفصحى واللهجات والإنجليزية ومزج اللغات.
- تحليل الحالات التي يرفضها النظام ومن يتحمل الرفض.
- اختبار counterfactual مضبوط عندما يكون منطقيًا، دون اعتباره دليلًا وحيدًا.
- مراجعة نوعية مع خبراء وممثلين للمتأثرين، لا metrics فقط.

عدم وجود فرق إحصائي في عينة صغيرة لا يثبت الإنصاف.

### 5.4 المعالجة

- تحسين البيانات والتمثيل وguidelines وفق `DATA_QUALITY_ARCHITECTURE.md`.
- تغيير الهدف أو threshold أو workflow إذا كان الضرر من تصميم القرار.
- human review مدرب مع ضوابط تمنع automation bias.
- abstain/escalate عند عدم الثقة أو خارج نطاق الدعم.
- إعلان حدود الدعم بدل إسقاط الفئات الصعبة من القياس.
- عدم استخدام سمة حساسة للمعالجة دون أساس قانوني وتحليل أثر.
- إيقاف use case إذا تعذر خفض الضرر إلى مستوى مقبول.

## 6. الشفافية للمستخدم

قبل الإرسال يجب أن يستطيع المستخدم فهم:

- أنه يتعامل مع AI أو Demo، وأيهما فعال الآن.
- الغرض والقدرات غير المتاحة والحدود المعروفة.
- أن المخرجات قد تكون خاطئة أو قديمة أو منحازة.
- هل سترسل البيانات إلى Backend أو مزود خارجي.
- ما يُحفظ ولماذا ومدة الحفظ وكيفية الحذف عند التنفيذ.
- هل توجد تكلفة أو حصة أو أثر خارجي.
- متى تكون مراجعة بشرية مطلوبة وكيف يطلبها.
- كيف يبلغ عن خطأ أو ضرر أو يعترض على نتيجة.

لا تُخفى المعلومات الجوهرية داخل سياسة طويلة فقط؛ يظهر contextual notice عند نقطة
القرار، مع رابط للتفاصيل.

## 7. مستويات الشفافية الفنية

التوثيق المقترح لكل قدرة/model deployment:

### System Card

- الغرض والنطاق والمستخدمون والاستخدامات المحظورة.
- المكونات والمزود وتدفقات البيانات وحدود الثقة.
- SLO والحصة والتكلفة والسلوك عند الفشل.
- human oversight والاعتراض والحوادث.

### Model/Provider Card

- model/version أو alias ومدى ثباته.
- بيانات أو منهجية معلنة رسميًا من المزود، مع توضيح ما هو مجهول.
- اللغات والقدرات والقيود والتقييمات المتاحة.
- سياسات الاحتفاظ والتدريب وZDR ومستوى الخدمة بحسب الخطة.
- تاريخ التحقق ومصدر كل معلومة.

### Data Card

- المصدر والترخيص والتمثيل والجودة والخصوصية والإصدار وفق وثيقة جودة البيانات.

### Evaluation Card

- المهام والمقاييس والشرائح والبيئة والنتائج والفشل والاستثناءات.
- الفرق بين mock واختبار المزود الحقيقي.

لا يوجد حاليًا model/system/data/evaluation card معتمد لإطلاق عام: `NOT_IMPLEMENTED`.

## 8. قابلية التفسير

### 8.1 ما هو تفسير مقبول؟

بحسب نوع النظام، يمكن أن يشمل:

- القاعدة أو السياسة التي تسببت في السماح/الرفض.
- مصادر ومستندات مقتبسة مع تاريخها إذا استخدم RAG.
- عوامل دخلت القرار وكيف أثرت فيه ضمن حدود مثبتة.
- درجة ثقة calibrated إن كانت موجودة ومفهومة، لا نسبة مصطنعة.
- البدائل الممكنة وما الذي يستطيع المستخدم تغييره قانونيًا.
- حدود المعرفة وما لم يستخدمه النظام.

### 8.2 ما ليس تفسيرًا موثوقًا؟

- نص يولده النموذج بعد النتيجة ويبدو منطقيًا بلا إثبات ارتباط سببي.
- كشف chain-of-thought باعتباره سجل قرار دقيقًا.
- إسناد قرار مزود مغلق إلى weights أو بيانات تدريب غير متاحة.
- citations غير متحقق منها أو روابط لا تدعم الادعاء.
- confidence رقمية غير calibrated.
- feature importance عام لتفسير قرار فردي دون تحقق مناسب.

لا يُطلب أو يُخزن reasoning داخلي سري لتقديمه للمستخدم. التفسير يُبنى من الأدلة
القابلة للتدقيق: inputs المسموحة، قواعد النظام، tool calls المصرح بها، المصادر،
إصدارات المكونات، والقرار البشري.

### 8.3 التفسير في التطبيقات الحساسة

قبل أي استخدام حساس يجب أن يستطيع reviewer:

- إعادة بناء المدخلات والإصدار والسياسات والمصادر دون كشف بيانات لغير مخول.
- فهم حدود النموذج والبدائل وسبب التصعيد أو الرفض.
- تصحيح بيانات خاطئة وإعادة التقييم بإجراء مضبوط.
- تجاوز التوصية مع سبب مسجل دون عقوبة آلية.
- شرح القرار النهائي بلغة مفهومة للمتأثر، مع حق الاعتراض.

إذا كان المزود المغلق لا يوفر شفافية كافية للمخاطر، لا يُستخدم لذلك القرار.

## 9. التحقق من الاستشهادات والحقائق

إذا أضيف RAG أو مصادر مستقبلًا:

- كل citation ترتبط بمقطع فعلي وإصدار وتاريخ وصلاحية وصول.
- التحقق أن المصدر يدعم الادعاء، لا مجرد تشابه كلمات.
- تمييز المصدر الأولي من الرأي أو المحتوى المولد.
- الإفصاح عن تعارض المصادر أو قدمها.
- عدم اختلاق citation عند غياب دليل؛ يُرفض أو يُقال غير معروف.
- ACL يطبق قبل retrieval وبعده لمنع تسريب tenant.
- prompt injection داخل المستند لا يغير policy أو الصلاحيات.

RAG والاستشهادات غير منفذة ولا يجوز الإعلان عنها.

## 10. الإشراف البشري

“Human in the loop” ليس مجرد زر موافقة. يجب تحديد:

- من يراجع، وما خبرته وصلاحيته ووقته المتاح.
- المعلومات التي يراها لاتخاذ قرار مستقل.
- متى يكون review إلزاميًا ومتى يرفض النظام تلقائيًا.
- كيفية منع rubber-stamping وautomation bias.
- sampling ومراجعة جودة قرارات البشر أيضًا.
- قدرة reviewer على التعديل والرفض والتصعيد.
- سجل القرار والسبب وحقوق الشخص المتأثر.
- إدارة التعارض والمناوبة والحوادث.

في الاستخدامات عالية الأثر يجب أن يكون القرار البشري ذا معنى وليس تصديقًا شكليًا.
نموذج الإشراف والمالكون: `NOT_DECIDED`.

## 11. المساءلة والملكية

قبل الإنتاج يُعتمد RACI أو ما يعادله:

| المسؤولية | الدور المطلوب | الحالة |
|---|---|---|
| اعتماد الغرض والمخاطر | Product/Business Owner | `NOT_ASSIGNED` |
| النموذج والتقييم | ML/System Owner | `NOT_ASSIGNED` |
| جودة البيانات وحقوقها | Data Owner/Steward | `NOT_ASSIGNED` |
| الأمن والخصوصية | Security/Privacy Owner | `NOT_ASSIGNED` |
| التقييم القانوني | Legal/Compliance Reviewer | `NOT_ASSIGNED` |
| القرار الحساس النهائي | Qualified Human Authority | `NOT_ASSIGNED` |
| التشغيل والحوادث | Operations/Incident Owner | `NOT_ASSIGNED` |
| شكاوى واعتراضات المستخدم | Support/Appeals Owner | `NOT_ASSIGNED` |

لا يُنسب الضرر إلى “الخوارزمية” كفاعل مستقل. الجهة التي تعتمد الاستخدام تحتفظ
بالمسؤولية عن الاختيار والمراقبة والتدخل والتعويض وفق القانون.

## 12. الاعتراض والتصحيح والإنصاف الإجرائي

إذا أثرت نتيجة في شخص:

- إخطار مفهوم باستخدام AI ودوره في النتيجة، حيث يلزم.
- قناة اعتراض متاحة وغير تمييزية ولا تتطلب معرفة تقنية.
- مراجعة بشرية مستقلة ضمن زمن معلن.
- إمكانية تصحيح البيانات غير الدقيقة وتتبع أثر التصحيح.
- عدم الانتقام أو تخفيض الخدمة بسبب الاعتراض.
- حفظ الأدلة اللازمة فقط بصلاحيات ومدة محددتين.
- إبلاغ النتيجة والسبب والخطوة التالية.
- تصعيد للأضرار الجسيمة ومسار remedy يحدده المختصون.

آلية appeal/remedy وSLA: `NOT_IMPLEMENTED`؛ لذلك القرار الآلي عالي الأثر محظور.

## 13. الخصوصية

- purpose limitation وdata minimization قبل الجمع.
- لا تدريب أو تقييم بمحادثات المستخدم افتراضيًا.
- موافقة منفصلة ومفهومة وقابلة للسحب إذا كانت الأساس المناسب.
- فصل session state ومحتوى المحادثة والتدقيق والتشغيل.
- تشفير ونطاقات وصول وretention وحذف وفق `SECURITY_ARCHITECTURE.md`.
- منع prompts والردود والسمات الحساسة من logs وanalytics افتراضيًا.
- عدم استخدام pseudonymization كادعاء anonymity.
- منع inference لسمات حساسة دون ضرورة ومشروعية ومراجعة.
- DPIA أو تقييم أثر مناسب قبل معالجة عالية الخطورة أو واسعة النطاق.
- مراجعة شروط المزود وDPA/ZDR ومكان المعالجة قبل البيانات الحساسة.

الامتثال لـGDPR/HIPAA والقانون المصري ليس مثبتًا؛ يحتاج تقييم انطباق قانوني.

## 14. السلامة ومنع الضرر

لكل use case threat/harm model يشمل:

- ضرر جسدي أو نفسي أو مالي أو قانوني أو سمعة.
- تضليل وهلوسة ومعلومة قديمة.
- كراهية أو تحرش أو تحيز أو إقصاء.
- سوء استخدام متعمد وprompt injection وjailbreak.
- كشف بيانات أو إعادة تعريف أفراد.
- over-reliance وautomation bias.
- أثر رفض الخدمة أو كثرة false positives.
- ضرر بيئي أو تكلفة غير منضبطة.

الضوابط متعددة الطبقات: نطاق واضح، validation، أقل صلاحية، policy checks، human
review، refusal، monitoring، kill switch، وحوادث. safety filter واحد أو disclaimer
لا يكفي.

## 15. التقييم الأخلاقي والاختبارات

قبل اعتماد قدرة AI:

- تقييم جودة على مهام وتمثيل واقعيين.
- fairness slices ومقاييس ضرر مناسبة.
- اختبارات العربية واللهجات والإنجليزية والـcode-switching.
- hallucination/factuality/citation tests حسب المهمة.
- privacy leakage وmemorization probes مصرح بها.
- prompt injection وjailbreak وtool misuse وdata exfiltration.
- calibration/abstention واختبار الحالات خارج النطاق.
- accessibility/usability لتأثير العرض على الإنصاف.
- red-team متعدد التخصصات للاستخدامات الحساسة.
- اختبار appeals/human override والحوادث وkill switch.

تُسجل prompts/fixtures بصورة صناعية أو منقحة. لا اختبار هجومي غير مصرح على المزود.
نجاح benchmark واحد لا يثبت العدالة أو السلامة العامة.

## 16. المراقبة بعد الإطلاق

إذا أُجيز إطلاق محدود:

- quality/safety/fairness metrics حسب شرائح مشروعة وبحجم كافٍ.
- drift في اللغة والمهام والمصادر والنتائج.
- معدلات الرفض والتصعيد والتجاوز البشري والاعتراض.
- شكاوى وأضرار مؤكدة ووقت المعالجة.
- تغير model alias أو سياسة المزود أو الاحتفاظ.
- unit cost والـlatency لأن الضغط المالي قد يغير الجودة والإنصاف.
- sampling لمراجعة بشرية مع تقليل البيانات.

التنبيه لا يعيد التدريب أو يوسع الصلاحيات تلقائيًا. لكل threshold إجراء: تحليل،
تقييد، rollback، kill switch، أو إخطار مناسب.

## 17. الحوادث والإبلاغ

حادث أخلاقي/AI قد يشمل:

- قرار تمييزي أو ضرر متكرر لشريحة.
- توصية عالية الأثر غير مصرح بها.
- تسريب بيانات أو استنتاج سمة حساسة.
- citation مزورة سببت ضررًا.
- tool action غير مصرح أو تكلفة كبيرة.
- اختلاف جوهري بعد تغيير نموذج من المزود.

الإجراء:

1. حماية المتأثرين ووقف/تقييد القدرة عند الحاجة.
2. حفظ أدلة منقحة مع سلسلة زمنية وإصدار المكونات.
3. إشراك الأمن والخصوصية والقانون وخبير المجال.
4. تقييم الإخطار والاعتراض والتصحيح وفق القانون.
5. تحليل السبب عبر البيانات والنموذج والسياسة والواجهة والبشر.
6. إصلاح واختبار مستقل قبل الاستعادة.
7. post-incident review وإجراء بمالك وموعد.

لا يوجد فريق أو SLA حوادث AI معين حاليًا: `NOT_ASSIGNED`.

## 18. إدارة المزود والتغييرات

قبل اعتماد مزود/نموذج:

- توثيق capabilities والقيود واللغات والتقييمات الرسمية.
- مراجعة شروط البيانات والاحتفاظ والتدريب والمراجعة البشرية وZDR.
- معرفة إن كان model alias قد يتغير دون إشعار وكيفية pinning إن أمكن.
- اختبار مستقل لا الاعتماد على model card تسويقية فقط.
- بند إخطار للتغييرات والحوادث حيث تسمح الخطة/العقد.
- خطة خروج وتصدير/حذف البيانات وتبديل المزود دون توسيع استخدام البيانات.

تغيير model version يعامل كتغيير سلوكي: regression/fairness/safety/cost evaluation
وموافقة قبل rollout. لا fallback لمزود ثانٍ دون مراجعة مستقلة.

## 19. التواصل العام والادعاءات

يُمنع نشر ادعاءات مثل:

- “غير متحيز” أو “عادل للجميع”.
- “قابل للتفسير بالكامل”.
- “دقيق 100%” أو “خالٍ من الهلوسة”.
- “متوافق مع GDPR/HIPAA” دون تقييم ودليل مناسب.
- “لا يحتفظ بالبيانات” دون تحقق الخطة والمزود والتشغيل.
- “يراجعه إنسان” دون workflow فعلي ومالك وزمن.
- “آمن للطب/القانون” دون اعتماد متخصص وقانوني.

كل claim يحتاج تعريف metric ونطاقًا وتاريخًا وإصدارًا ومصدر دليل وقيودًا واضحة.

## 21. بوابات الجاهزية

### مسموح الآن

- Demo معلّم بوضوح ببيانات غير حساسة.
- اختبار محلي لمهام منخفضة المخاطر دون أثر خارجي.
- إعداد use-case/harm/evaluation cards دون ادعاء اعتماد.
- إضافة نصوص شفافية واختبارات صدق الحالة.

### مانع لإطلاق قدرة AI عامة

- لا مزود/نموذج وسياسة بيانات وهوية معتمدة.
- لا use-case classification أو harm assessment أو مالك قرار.
- لا evaluation dataset أو جودة/سلامة/fairness thresholds.
- لا system/model/data/evaluation cards معتمدة.
- لا human oversight أو appeals أو incident ownership.
- لا تقييم خصوصية وقانون وحقوق للبيانات والاستخدام.
- لا اختبار اختراق/red-team مناسب للسطح.
- بوابات الأمن والموثوقية والتكلفة والبيانات ما زالت مفتوحة.

### شرط تغيير الحالة

لا تصبح الأخلاقيات `APPROVED` بوجود سياسة مكتوبة أو disclaimer. يلزم دليل اختبار
مؤرخ لكل use case وإصدار، مشاركة خبراء ومتأثرين مناسبة، تعريف مسؤوليات واعتراض،
تحقق خصوصية وقانون، مراقبة وkill switch، وموافقة بشرية صريحة على المخاطر المتبقية.
