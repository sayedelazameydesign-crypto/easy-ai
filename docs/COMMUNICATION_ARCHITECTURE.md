# Cela.sh — Communication Architecture Design (P1-D)

> **الحالة:** مسودة معمارية للمراجعة البشرية، وليست تنفيذًا.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** تصميم عقود وسياسات اتصال مشتركة دون إضافة ناقل أو مكتبة أو خدمة.

## 1. الهدف والمبادئ

تهدف هذه الوثيقة إلى وضع حدود واضحة بين منطق الوكيل ووسائل النقل وموصلات الأدوات،
مع توحيد ما يمكن توحيده بأمان: الهوية، الصلاحيات، المهل، الإلغاء، أحجام البيانات،
معرّفات التتبع، الأخطاء والتدقيق. لا تهدف إلى إخفاء اختلاف البروتوكولات خلف واجهة
مصطنعة واحدة؛ فـHTTP وSSE وMCP وقواعد البيانات والطوابير لها دلالات تشغيل مختلفة.

المبادئ الحاكمة:

1. **أقل تعقيد يحقق حاجة مثبتة:** يبقى HTTP/HTTPS أساس الإصدار الأول.
2. **الصلاحية لا تتسع عبر النقل:** لا تمنح طبقة الاتصال أداة صلاحيات أعلى من
   الوكيل أو المستخدم الذي بدأ العملية.
3. **الفشل صريح:** لا يتحول انقطاع قناة حقيقية إلى نجاح أو رد تجريبي صامت.
4. **البيانات مقيدة قبل النقل:** التحقق والحجم والتصنيف والمهلة تسبق الاتصال.
5. **الأسرار خارج الحمولة والسجلات:** تُحقن من مخزن أسرار في الحد الموثوق فقط.
6. **كل ناقل يحتفظ بخصائصه:** العقود المشتركة لا تلغي backpressure أو ordering أو
   delivery semantics الخاصة بكل قناة.
7. **لا بروتوكول احترازي:** WebSocket وgRPC والوسطاء لا تُضاف لمجرد احتمال الحاجة.

## 2. النطاق وخارج النطاق

### داخل نطاق التصميم

- طلبات API النصية الحالية وحالاتها.
- بث أحادي الاتجاه محتمل للإجابات وتقدم المهام.
- موصلات أدوات محلية وبعيدة مستقبلية.
- سياسات مشتركة للمصادقة والتفويض والمهل والأحجام والتدقيق.
- تصنيف التقنيات إلى مطلوبة ومشروطة ومؤجلة.

### خارج النطاق

- اختيار مزود نموذج أو منصة استضافة؛ هذا قرار مستقل بعد مراجعة P1-C.
- تنفيذ SSE أو MCP أو أي ناقل جديد.
- إنشاء وكيل ذاتي أو نظام أدوات.
- تعديل قناة المزامنة أو manifest أو التنقيح.
- ضمان exactly-once عام؛ معظم الشبكات والوسطاء لا يقدمونه من طرف إلى طرف.
- تصميم مخطط قاعدة بيانات أو نظام هوية كامل.

## 3. حدود المسؤولية

```text
المستخدم / واجهة العميل
        │ نية + سياق + هوية
        ▼
منسق الوكيل أو المهمة
        │ يقرر ماذا يُستدعى ولماذا وبأي صلاحية
        ▼
طبقة سياسة الاتصال
        │ تحقق، تفويض، مهلة، حجم، allowlist، request_id، تدقيق
        ▼
موصل الأداة / Adapter المزود
        │ يحول العقد العام إلى عقد البروتوكول أو المزود
        ▼
ناقل محدد: HTTP | SSE | MCP | DB driver | Queue | ...
        │
        ▼
الأداة أو المزود أو الخدمة
```

### 3.1 الوكيل أو منسق المهمة

مسؤول عن:

- تحديد هدف العملية والقدرة المطلوبة.
- طلب أقل مجموعة صلاحيات لازمة.
- تمرير سياق مصنف ومحدود، لا كامل ذاكرة المستخدم افتراضيًا.
- تفسير النتيجة على مستوى المنتج.
- طلب موافقة المستخدم قبل العمليات الحساسة أو ذات الأثر الخارجي.

غير مسؤول عن:

- تكوين ترويسات المصادقة الخاصة بكل مزود.
- إعادة المحاولة الشبكية منخفضة المستوى.
- اختيار عنوان عشوائي أو تجاوز allowlist.
- تخزين الأسرار.

### 3.2 طبقة سياسة الاتصال

مسؤولة عن:

- ربط هوية المستدعي بالصلاحيات الفعلية.
- إنشاء وتمرير معرّفات الطلب والمهمة والمحاولة.
- فرض deadline وحدود الحمولة والمخرجات.
- اختيار connector مسجل مسبقًا؛ لا تقبل عنوانًا أو أمرًا اعتباطيًا من المستخدم.
- تطبيق سياسة إعادة المحاولة والإلغاء والتدقيق.
- تحويل أخطاء الناقل إلى تصنيف آمن مشترك دون تسريب التفاصيل الداخلية.

لا تُعيد كتابة semantics الناقل، ولا تدعي أن رسالة queue مساوية لطلب HTTP متزامن.

### 3.3 موصل الأداة أو المزود

مسؤول عن:

- التحقق من مخطط الأداة المحدد وتحويله إلى بروتوكولها.
- تثبيت endpoint أو command أو DSN من إعداد خادمي موثوق.
- إضافة credential من مخزن الأسرار عند الحد الأخير الممكن.
- احترام مهلة الاتصال والقراءة وحدود الرد.
- إزالة أجسام أخطاء الطرف الثالث من الخطأ العام.
- إعلان خصائصه: read/write، قابلية الإعادة، التدفق، الإلغاء، الحد الأقصى.

### 3.4 الناقل

مسؤول عن نقل bytes/frames/messages وفق خصائصه فقط. لا يقرر صلاحية المستخدم أو
جواز استدعاء الأداة، ولا يصبح طبقة ثقة لمجرد استخدام TLS.

## 4. العقود المشتركة المفاهيمية

هذه مخططات تصميمية وليست API منفذة بعد.

### 4.1 غلاف طلب الاتصال

```text
CommunicationRequest
  request_id: UUID/ULID يولده الحد الأول الموثوق
  task_id: اختياري؛ ثابت عبر طلبات المهمة الواحدة
  parent_request_id: اختياري؛ لربط الاستدعاءات المتفرعة
  actor:
    principal_id: معرف داخلي غير حساس
    principal_type: user | service | agent
    delegated_by: اختياري
  capability: اسم قدرة مسجلة، لا URL أو shell command
  operation: اسم عملية داخل القدرة
  input: حمولة تم التحقق منها وفق schema خاص بالموصل
  data_classification: public | internal | confidential | restricted
  deadline_at: وقت مطلق، لا timeout مفتوح
  idempotency_key: اختياري ومسموح فقط لعمليات معلنة
  consent_ref: اختياري للعمليات التي تحتاج موافقة
  trace_context: بيانات تتبع غير سرية ومحدودة
```

قواعد:

- لا يثق الخادم في `request_id` القادم من عميل عام دون تحقق؛ يمكنه استبداله مع
  حفظ client correlation منفصلًا.
- `task_id` للتجميع والتدقيق وليس صلاحية وصول.
- `deadline_at` ينتقل تنازليًا؛ لا يجوز للموصل تمديد مهلة المستدعي.
- لا تُقبل credentials أو endpoint داخل `input`.

### 4.2 غلاف النتيجة

```text
CommunicationResult
  request_id
  task_id
  status: ok | partial | cancelled | error
  output: حمولة محدودة وفق schema
  error: CommunicationError أو null
  usage: counters غير مالية بالضرورة (bytes, tokens, attempts)
  started_at / completed_at
  provider_request_id: اختياري، منقح وآمن للتشخيص
```

`partial` لا تعني نجاحًا كاملًا؛ يجب أن يحدد الموصل ما الذي اكتمل وما الذي لم
يكتمل. لا تُعاد بيانات خام للمزود أو stack trace إلى العميل.

### 4.3 تصنيف الأخطاء المشترك

```text
invalid_request       مخطط أو نوع أو حجم غير صالح
unauthenticated       لا توجد هوية صحيحة
permission_denied     الهوية لا تملك القدرة/العملية
approval_required     تحتاج موافقة بشرية
not_configured        الموصل أو السر غير مهيأ
not_found             مورد مصرح به غير موجود
conflict              تعارض حالة أو idempotency
rate_limited          حد داخلي أو لدى المزود
cancelled             إلغاء معروف
deadline_exceeded     انتهاء deadline محلي أو بعيد
unavailable           انقطاع مؤقت/فتح circuit
provider_error        فشل خارجي آمن غير مصنف
internal_error        خطأ داخلي عام دون تفاصيل
```

يحتوي الخطأ العام على `code` و`retryable` و`safe_message_key` و`request_id` فقط
عند الحاجة. التفاصيل الداخلية تبقى في قناة تشغيل مقيدة ومنقحة.

## 5. معرّفات الطلب والمهمة والتتبع

- ينشأ `request_id` عند API gateway أو أول عملية موثوقة، ويمر في HTTP header أو
  metadata أو رسالة queue حسب الناقل.
- يبقى `task_id` ثابتًا طوال المهمة متعددة الخطوات، بينما لكل استدعاء `request_id`.
- كل retry يأخذ `attempt` جديدًا مع نفس المفتاح المنطقي عند السماح بذلك.
- لا تُستخدم عناوين البريد أو أسماء الملفات أو prompts كمعرّفات.
- لا توضع الأسرار أو المحتوى في trace baggage.
- يجب منع العميل من حقن trace headers غير محدودة أو توجيه السجلات لمستأجر آخر.

أسماء أولية قابلة للمراجعة:

```text
X-Request-ID
X-Task-ID
Idempotency-Key
traceparent
```

لا تُعتمد هذه الأسماء كعقد عام حتى تثبيت معيار API.

## 6. المهل والإلغاء

### 6.1 الميزانية الزمنية

تقسم المهلة الكلية إلى:

1. انتظار في queue إن وجدت.
2. اتصال DNS/TCP/TLS.
3. إرسال الطلب.
4. انتظار أول byte/event.
5. قراءة الرد أو التدفق.
6. معالجة محلية قصيرة.

على كل موصل استخدام المهلة المتبقية، لا إعادة بدء timeout كامل. عند انتهاء
`deadline_at` يجب إيقاف العمل قدر الإمكان وإرجاع `deadline_exceeded`.

### 6.2 الإلغاء

- HTTP العادي: إغلاق العميل لا يضمن إلغاء عمل المزود؛ يحتاج connector إلى cancellation
  إن كان المزود يدعمها.
- SSE: إغلاق stream إشارة إلغاء، لكنه لا يثبت توقف المهمة الخلفية.
- MCP stdio: يحتاج lifecycle واضحًا وإغلاق process مضبوطًا.
- Queue: الإلغاء رسالة/حالة مستقلة ويجب منع worker من commit بعد إلغاء نهائي.
- Database: استخدم statement timeout وإلغاء driver حيث يتوفر.

الإلغاء best-effort ما لم يقدم النظام ضمانًا أقوى موثقًا.

### 6.3 حدود الزمن والاستهلاك والتكلفة

هذه الحدود مستقلة ولا يحل أحدها محل الآخر. لا تُختار قيم رقمية قبل اعتماد المزود
والاستضافة:

| الحد | الغرض | موضع الإنفاذ المتوقع | السلوك عند التجاوز |
|---|---|---|---|
| `connect_timeout` | منع تعليق DNS/TCP/TLS أو إنشاء الاتصال | HTTP client/driver داخل connector | قطع المحاولة وإرجاع `deadline_exceeded` أو `unavailable` وفق السبب؛ retry محدود إن بقيت ميزانية |
| `read_timeout` | منع انتظار أول byte أو توقف القراءة بلا حد | client/driver لكل قراءة أو فترة خمول stream | قطع القراءة؛ لا يعرض رد جزئي كنجاح كامل |
| `task_deadline` | سقف زمني مطلق للمهمة بكل queue/retries/processing | منسق المهمة، ويمر كوقت مطلق لكل طبقة | إلغاء best-effort ومنع بدء محاولة جديدة وإرجاع `deadline_exceeded` |
| حد مخرجات النموذج | تقييد tokens/bytes الناتجة وتقليل زمن وتكلفة الطلب | طلب المزود ثم تحقق الرد في adapter | طلب حد من المزود واقتطاع/رفض آمن حسب العقد؛ ليس ضمانًا ماليًا |
| حد تكلفة لكل طلب | منع طلب مقدر أنه أعلى من ميزانية العملية | طبقة سياسة الاتصال قبل الإرسال، ثم reconcile بعد usage الفعلي | رفض قبل الاتصال أو تعليم العملية `cost_limit_exceeded` مستقبلًا؛ التقدير لا يساوي فاتورة نهائية |
| الحصة الإجمالية/حد الإنفاق | حماية المشروع أو tenant عبر فترة زمنية | بوابة موزعة + ضابط المزود/الفوترة إن كان قابلًا للإنفاذ | وقف طلبات جديدة وفتح kill switch؛ التنبيه وحده لا يكفي |

حد tokens لا يساوي حدًا ماليًا؛ فقد تختلف أسعار الإدخال والإخراج والأدوات والنماذج.
ومحدد المعدل لا يضمن عدم تجاوز التكلفة، لأن الطلب الواحد قد يكون غاليًا ولأن الحصة
قد تتراكم مع الزمن. كذلك budget alert ليس hard stop ما لم توثق المنصة رفض الطلبات
عند تجاوزه. إذا لم يقدم المزود hard cap مثبتًا، يلزم prepaid محدود بلا auto-recharge
حيث أمكن، quota موزعة، ومفتاح إيقاف مختبر قبل النشر العام.

فشل المزود أو نفاد الحصة أو فتح kill switch ينتج حالة خطأ/عدم توفر صريحة. لا يجوز
التحول إلى ردود تجريبية وعرضها على أنها إجابات نموذج حقيقي.

## 7. المصادقة والتفويض والتفويض المتسلسل

### 7.1 الهوية

- المستخدم العام يُصادق عند gateway؛ لا تمر كلمة المرور إلى الموصلات.
- service identity مستقلة لكل خدمة، ولا تستخدم مفتاحًا مشتركًا شاملًا.
- الأداة المحلية ترث capability محددة، لا كامل بيئة عملية الوكيل.
- remote connector يتحقق من TLS والهوية المقابلة، ويمكن استخدام mTLS للخدمات
  الداخلية عند وجود بنية شهادات تبرر ذلك.

### 7.2 التفويض

يُفحص على مستويين:

1. هل actor مسموح له باستخدام capability؟
2. هل مسموح له بهذه operation وعلى هذا resource والنطاق؟

التمثيل المفاهيمي لكل صلاحية مقيدة هو:

```text
Permission = (tenant, capability, operation, resource)
```

- `tenant`: حد العزل الذي لا يجوز لمعرف أو مورد تجاوزه.
- `capability`: الموصل أو القدرة المسجلة، لا عنوانًا ديناميكيًا.
- `operation`: فعل محدد مثل `read` أو `create`، لا wildcard افتراضيًا.
- `resource`: مورد بعينه أو نطاق موارد محدود يمكن مطابقته بصورة حتمية.

قاعدة عدم توسيع الصلاحية:

```text
EffectivePermissions = CallerPermissions ∩ AgentPermissions ∩ ConnectorPolicy
```

التقييم **deny-by-default**: غياب سماح مطابق للتركيبة الكاملة يعني الرفض. أي منع
صريح في سياسة قابلة للتطبيق له أولوية على السماح، ولا يمكن لسماح أوسع أن يلغي منعًا
أضيق. لا يستطيع الوكيل تفويض أداة بصلاحية لا يملكها، ولا يستطيع connector تجاوز
الموافقة بحجة أن credential الخادمي أقوى. شكل claims، قواعد resource matching،
وتخزين السياسات تفاصيل مؤجلة إلى تصميم نظام الأدوات؛ لا يجوز تنفيذها كمطابقة نصية
مرتجلة.

### 7.3 الموافقات

تحتاج موافقة بشرية صريحة، مثلًا:

- إرسال بريد أو نشر محتوى.
- تعديل/حذف بيانات خارجية.
- تنفيذ أمر بعيد أو رفع ملف.
- عملية مالية أو تغيير صلاحيات.

الموافقة مرتبطة بـactor وoperation وresource وملخص أثر ومدة قصيرة؛ ليست موافقة
مفتوحة لكل عمليات الأداة.

## 8. حدود البيانات وحمايتها

- لكل connector schema وحد أقصى للطلب والرد وعدد العناصر/الرسائل.
- الملفات تُفحص حسب MIME والحجم والمحتوى، ولا يُثق باسم الامتداد.
- التصنيف `restricted` يمنع الخروج إلى مزود لا تسمح سياسته بذلك.
- تُزال الحقول غير المعروفة fail-closed أو يُرفض الطلب؛ لا تمرر تلقائيًا.
- تمنع redirects إلى عناوين غير مسموحة، مع إعادة التحقق بعد كل redirect إن سمح به.
- DNS/IP validation يمنع loopback وlink-local وmetadata/private ranges للاتصال
  الخارجي، مع حماية DNS rebinding.
- response decompression يخضع لحد لمنع zip/decompression bombs.
- لا تُخزن أجسام الطلب والرد افتراضيًا، ولا تدخل prompts في analytics.

هذه متطلبات تصميمية وليست تنفيذًا قائمًا. قبل إنشاء أي connector يسمح بوجهة
ديناميكية يجب اعتماد threat model وخوارزمية تحقق تفحص scheme/host/port، وتحل كل
عناوين A/AAAA، وترفض أي عنوان محظور، وتربط الاتصال بالوجهة التي تم التحقق منها
لمنع DNS TOCTOU/rebinding، ثم تعيد العملية كاملة بعد كل redirect. إلى أن يحدث ذلك،
تبقى endpoints ثابتة ومسجلة خادميًا ولا يقبل النظام URL من المستخدم أو النموذج.

## 9. إعادة المحاولة وIdempotency

### 9.1 متى تُسمح الإعادة

| العملية | الإعادة التلقائية |
|---|---|
| GET/قراءة بلا أثر | ممكنة بحد صغير مع backoff وjitter |
| توليد نموذج | بحذر؛ قد يستهلك تكلفة مرتين، ويحتاج مفتاح/دعم مزود إن توفر |
| إنشاء مورد | فقط مع idempotency key مدعوم ومخزن نتيجة موثوق |
| تعديل/حذف | لا افتراضيًا؛ يحتاج version/ETag أو عقدًا خاصًا |
| إرسال بريد/دفع/نشر | ممنوعة دون deduplication مؤكد |
| رسالة Queue | وفق delivery semantics وdeduplication/DLQ |

### 9.2 السياسة

- لا retry لأخطاء 4xx الدائمة، باستثناء حالات محددة مثل 408/429 وفق `Retry-After`.
- retry محدود بعدد ومحكوم بالـdeadline وميزانية التكلفة.
- circuit breaker لكل destination يمنع عاصفة طلبات أثناء الانقطاع.
- idempotency key مرتبط بالactor والعملية وhash حمولة منقح ومدة صلاحية.
- تخزين نتيجة idempotency لا يحتوي أسرارًا أو ردودًا حساسة دون تشفير وسياسة احتفاظ.

## 10. التسجيل والتدقيق

### 10.1 سجل التشغيل

يسمح بـ:

- request/task IDs.
- connector وoperation وحالة عامة.
- زمن التنفيذ، عدد المحاولات وأحجام تقريبية.
- error code الآمن وprovider request ID المنقح.

يمنع افتراضيًا:

- Authorization/Cookie/API keys/DSN.
- prompt أو response أو body كامل.
- بريد أو هاتف أو أسماء ملفات حساسة.
- stack traces في ردود العملاء.

### 10.2 سجل التدقيق

يسجل العمليات ذات الأثر:

```text
who / delegated_by / capability / operation / resource_ref
approval_ref / outcome / request_id / timestamp
```

يكون append-oriented مع صلاحيات قراءة ضيقة ومدة احتفاظ معلنة. لا يعني tamper-evident
إلا إذا نُفذت آلية توقيع/ربط hash مستقلة مستقبلًا.

### 10.3 فصل حالة الجلسة والمحادثة والسجلات

لا يجوز دمج هذه الفئات في مخزن واحد أو معاملتها بسياسة احتفاظ واحدة:

| الفئة | الغرض | محتوى مسموح مبدئيًا | قرارات ما زالت مطلوبة |
|---|---|---|---|
| حالة الجلسة | تشغيل الطلب الجاري، منع التكرار وربط الهوية مؤقتًا | معرفات منقحة، حالة قصيرة العمر، لا سر مزود | مكان التخزين، TTL، الإبطال، التشفير وفصل tenant |
| محتوى المحادثة الاختياري | ميزة يستفيد منها المستخدم عند الحفظ الصريح | رسائل يوافق المستخدم على حفظها بعد تطبيق سياسة البيانات | opt-in/consent، مدة الاحتفاظ، الحذف والتصدير، التشفير ومن يقرأها |
| سجل التشغيل | تشخيص الأداء والأخطاء | metadata وأكواد آمنة دون prompt/response افتراضيًا | مدة الاحتفاظ والوصول وأخذ العينات |
| سجل التدقيق | إثبات العمليات ذات الأثر والموافقات | who/what/resource/outcome ومعرفات مرجعية منقحة | مدة قانونية، صلاحية القراءة، tamper evidence والحذف |

ذاكرة العملية وfilesystem المؤقت ليسا تخزينًا دائمًا لأي فئة. حفظ المحادثات ليس
نتيجة جانبية للتسجيل التشخيصي، وتعطيل logs لا يقرر تلقائيًا حذف سجل محادثة وافق
عليه المستخدم. إلى أن تعتمد قرارات consent/retention/deletion، لا يُفعّل حفظ دائم
لمحتوى المحادثة.

## 11. تصنيف الثقة

| المستوى | مثال | الافتراض والسياسة |
|---|---|---|
| T0 غير موثوق | متصفح عام، بريد وارد، webhook | تحقق كامل، مصادقة، rate limit، أحجام صغيرة، لا توجيه مباشر |
| T1 عميل مصادق | مستخدم داخل المنتج | صلاحيات مستخدم، موافقات للأثر، لا أسرار خادمية |
| T2 خدمة داخلية | Backend معروف | service identity، شبكة ليست ثقة، least privilege، تدقيق |
| T3 أداة محلية معزولة | MCP stdio process | sandbox، env منقحة، cwd/filesystem/network مقيدة |
| T4 مزود خارجي | نموذج، SaaS، SMTP | egress allowlist، TLS، سياسة بيانات، مهلة وتكلفة وحدود |
| T5 مخزن حساس | قاعدة بيانات/secret manager | حساب خدمة أدنى، queries مقيدة، audit، rotation |

الانتقال إلى مستوى أعلى لا يحدث تلقائيًا بسبب localhost أو private network.

## 12. تقييم وسائل الاتصال

### 12.1 HTTP/HTTPS

**يستخدم عندما:** request/response API، webhooks، مزودو النماذج، عمليات قصيرة أو
محدودة زمنيًا.

**لا يستخدم عندما:** نحتاج بثًا طويلًا بكفاءة، أو queue durable، أو throughput داخليًا
يبرر RPC typed.

**التعقيد:** منخفض؛ موجود مفاهيميًا في النظام الحالي.

**المخاطر والضوابط:** SSRF، redirects، header injection، أجسام ضخمة، timeouts،
retries مكررة، CORS. يلزم TLS، allowlist، schema، auth، rate limit وحدود اتصال/قراءة.

**قرار P1-D:** مطلوب في الإصدار الأول، ولا يُستبدل.

### 12.2 Server-Sent Events (SSE)

**يستخدم عندما:** بث tokens أو تقدم مهمة من الخادم إلى المتصفح مع قناة أحادية
الاتجاه وإعادة اتصال بسيطة.

**لا يستخدم عندما:** يحتاج العميل إرسال frames مستمرة ثنائية الاتجاه أو بروتوكول
تفاعلي منخفض الكمون في الاتجاهين.

**التعقيد:** منخفض إلى متوسط؛ HTTP مستمر، يحتاج heartbeat، event IDs، proxy buffering
وحدود اتصال متزامن.

**المخاطر والضوابط:** اتصالات معلقة، استئناف قد يكرر events، تسريب عبر event stream،
إلغاء غير مضمون. يلزم auth قبل فتح stream، `Cache-Control: no-store`، event size
limit، sequence IDs وسياسة resume واضحة.

**قرار P1-D:** يضاف فقط إذا أصبحت أولوية المنتج بث إجابات النموذج أو تقدم المهام.

### 12.3 WebSocket

**يستخدم عندما:** توجد حاجة مثبتة لاتصال ثنائي الاتجاه طويل العمر، مثل تعاون حي أو
تحكم تفاعلي مستمر لا يناسب HTTP+SSE.

**لا يستخدم عندما:** المحادثة request/response أو بث خادمي فقط.

**التعقيد:** متوسط إلى مرتفع؛ إدارة جلسات، reconnect، heartbeat، backpressure،
load balancer وstate distribution.

**المخاطر:** hijacking، رسائل غير محدودة، جلسات يتيمة، صعوبة revocation والتوسع.

**قرار P1-D:** مؤجل؛ SSE أبسط للحاجة المتوقعة.

### 12.4 MCP عبر stdio محلي

**يستخدم عندما:** تشغيل tool server محلي معروف مع lifecycle تابع للعملية وعزل واضح.

**لا يستخدم عندما:** البرنامج غير موثوق أو يحتاج multi-tenant remote access.

**التعقيد:** متوسط؛ process supervision، framing، schema negotiation، versioning.

**المخاطر:** command injection إن كانت الأوامر ديناميكية، تسريب env، وصول ملفات أو
شبكة مفرط، deadlock على stdout/stderr.

**الضوابط:** executable allowlist ثابت، argv بلا shell، env منقحة، cwd مؤقت، sandbox،
حدود موارد، stdout للبروتوكول فقط، قتل العملية عند deadline.

**قرار P1-D:** مشروط بتنفيذ نظام أدوات محلي، وليس جزءًا من محادثة الإصدار الأول.

### 12.5 MCP عبر Streamable HTTP بعيد

**يستخدم عندما:** tool server بعيد يطبق MCP وتوجد فائدة فعلية من discovery والعقود
المعيارية.

**لا يستخدم عندما:** API عادية محدودة تكفي، أو الخدمة لا تدعم MCP أصليًا.

**التعقيد:** متوسط إلى مرتفع؛ session/version negotiation، auth، streaming، توافق
إصدارات وتشغيل خدمة إضافية.

**المخاطر:** confused deputy، tool poisoning، تغيير schemas، SSRF عبر موارد الأدوات،
صلاحيات واسعة.

**الضوابط:** server allowlist، pinning للقدرات المسموحة، مراجعة schemas، موافقة
للأثر، فصل tenant، TLS ومصادقة قوية.

**قرار P1-D:** مؤجل حتى وجود نظام أدوات وحالة استخدام بعيدة مثبتة.

### 12.6 gRPC

**يستخدم عندما:** خدمات داخلية متعددة ذات عقود protobuf، throughput مرتفع، streaming
ثنائي أو تعدد لغات يبرر toolchain.

**لا يستخدم عندما:** خدمة Python واحدة وواجهة متصفح بسيطة.

**التعقيد:** مرتفع نسبيًا؛ protobuf generation، compatibility، HTTP/2، observability
وgateway للمتصفح.

**المخاطر:** رسائل كبيرة، deadlines غير ممرة، metadata secrets، compatibility breaks.

**قرار P1-D:** مؤجل حتى تقسيم خدمات داخلي مثبت وقياسات تبرره.

### 12.7 AMQP / RabbitMQ

**يستخدم عندما:** مهام غير متزامنة تحتاج durability، acknowledgements، retries،
routing وdead-letter queues.

**لا يستخدم عندما:** طلب محادثة متزامن بسيط أو حجم صغير يمكن معالجته مباشرة.

**التعقيد:** مرتفع؛ broker وتشغيل ومراقبة وDLQ وprefetch وdeduplication.

**المخاطر:** poison messages، redelivery، تراكم queue، ترتيب غير مضمون عالميًا،
تسريب بيانات في الرسائل.

**قرار P1-D:** مشروط بإضافة مهام خلفية طويلة تحتاج صفًا موثوقًا؛ ليس للإصدار الأول.

### 12.8 Kafka

**يستخدم عندما:** تدفق أحداث واسع ومستمر، replay واحتفاظ وتقسيم وعدة مستهلكين، مع
حجم يبرر منصة تشغيل مستقلة.

**لا يستخدم عندما:** queue مهام صغيرة أو تطبيق أحادي الخدمة.

**التعقيد:** عالٍ جدًا؛ cluster، partitions، schema registry، retention، consumer
lag وأمن تشغيلي.

**المخاطر:** بيانات حساسة محفوظة طويلًا، تكلفة، ordering داخل partition فقط، replay
غير آمن، صعوبة الحذف والامتثال.

**قرار P1-D:** مؤجل حتى قياسات حجم واحتياج replay مثبتة؛ لا توصية حالية بإضافته.

### 12.9 Database drivers وطبقة البيانات

**تستخدم عندما:** حالة دائمة، معاملات، بحث أو rate limits موزعة تحتاج قاعدة مناسبة.

**لا تستخدم كناقل أدوات عام:** SQL ليس بديلًا لعقد connector ولا يُعرض مباشرة
للوكيل أو المتصفح.

**التعقيد:** يعتمد على القاعدة؛ migrations، pooling، backup، isolation وschema.

**المخاطر:** injection، صلاحيات واسعة، استنزاف pool، معاملات طويلة، تسريب PII.

**الضوابط:** Adapter بيانات مستقل، parameterized queries، حسابات read/write منفصلة،
statement timeout، row/tenant isolation، migrations مراجعة وتشفير/نسخ احتياطية.

**قرار P1-D:** يضاف عند ظهور بيانات دائمة أو حاجة rate limiting موزع؛ لا قاعدة مطلوبة
لمجرد إضافة محادثة نصية محلية.

### 12.10 SSH/SFTP

**يستخدم عندما:** تكامل إداري متخصص ومصرح مع host ثابت لإدارة أو نقل ملفات.

**لا يستخدم:** لتنفيذ أوامر عامة يولدها النموذج أو كناقل افتراضي للأدوات.

**التعقيد والمخاطر:** إدارة مفاتيح وhost keys وshell quoting وصلاحيات نظام وaudit.
يلزم host allowlist وhost-key pinning ومستخدم محدود وcommand/file policy وموافقة.

**قرار P1-D:** تكامل متخصص مؤجل، لا قدرة أساسية للوكيل.

### 12.11 البريد الإلكتروني

**يستخدم عندما:** إرسال/استقبال رسائل كتكامل أعمال واضح.

**لا يستخدم:** كطابور موثوق أو قناة أوامر إدارية.

**المخاطر:** prompt injection في البريد الوارد، spoofing، مرفقات، PII، إرسال غير قابل
للتراجع وتكرار الرسائل.

**الضوابط:** تحقق SPF/DKIM/DMARC كإشارات لا ثقة مطلقة، فحص مرفقات، موافقة قبل
الإرسال، recipient allowlist، deduplication وتدقيق.

**قرار P1-D:** موصل متخصص فقط عند اعتماد ميزة بريد محددة.

## 13. التعامل مع الانقطاع وتوقف المزود

- تصنف الأعطال إلى transient وpermanent وpolicy/billing.
- transient قد يخضع retry محدودًا؛ billing/auth/config لا يُعاد تلقائيًا.
- circuit breaker يفتح عند فشل متكرر ويعيد `unavailable` بسرعة.
- الواجهة تعرض حالة صريحة ولا تقدم ردًا ثابتًا على أنه رد المزود.
- المهمة غير المتزامنة تنتقل إلى delayed retry أو DLQ وفق عقدها، لا loop بلا حد.
- لا failover إلى مزود آخر إلا بعد اعتماد سياسة بيانات وتكلفة وتوافق مستقلة؛ تغيير
  المزود قد يغير الخصوصية وجودة النتيجة.
- degraded mode معلن بوضوح، مثل تعطيل الأدوات الخارجية مع إبقاء وظائف محلية آمنة.

## 14. مراحل التنفيذ المقترحة

### الإصدار الأول — مطلوب فقط

- HTTP/HTTPS لـ`/api/status` و`/api/chat`.
- العقود الحالية المحدودة للأخطاء والأحجام والمهل.
- مصادقة/بوابة وصول قبل أي إتاحة عامة.
- request ID داخلي آمن وسجل تشغيل منقح.
- egress allowlist وعنوان مزود ثابت.
- rate limit قابل للإنفاذ في منصة النشر المختارة.

لا تتضمن هذه المرحلة SSE أو MCP أو WebSocket أو وسيط رسائل.

### عند إضافة قدرة محددة

| القدرة | التقنية المرشحة | شرط البدء |
|---|---|---|
| بث إجابة/تقدم للمتصفح | SSE | UX يحتاج تحديثًا تدريجيًا ويدعم المزود streaming |
| أدوات محلية | MCP stdio | tool registry وصلاحيات وsandbox وموافقات معتمدة |
| أدوات بعيدة معيارية | MCP Streamable HTTP | خادم MCP معروف وحاجة discovery مثبتة |
| مهام خلفية durable | RabbitMQ/AMQP أو خدمة queue مُدارة | مهام طويلة وفشل/إعادة موثق وحاجة DLQ |
| حالة دائمة/rate limit موزع | Database/Key-Value adapter | اختيار استضافة وSLA وبيانات مطلوب حفظها |
| اتصال ثنائي حي | WebSocket | SSE+HTTP غير كافيين بقياس واضح |
| خدمات داخلية متعددة | gRPC | فصل خدمات وthroughput/tooling يبرر التعقيد |

### مؤجل حتى حاجة وقياسات مثبتة

- Kafka.
- WebSocket العام.
- gRPC.
- SSH/SFTP.
- البريد الإلكتروني.
- failover تلقائي بين مزودي النماذج.

## 15. سجل قرارات أولي

| القرار | الحالة | السبب |
|---|---|---|
| إبقاء HTTP/HTTPS | موصى به للمراجعة | موجود ويكفي عقد المحادثة الحالي |
| SSE هو أول ناقل إضافي محتمل | مشروط | أبسط من WebSocket لبث خادمي أحادي الاتجاه |
| MCP ليس ضمن الإصدار الأول | موصى به | لا يوجد نظام أدوات معتمد بعد |
| عدم إضافة broker | موصى به | لا توجد مهام durable مثبتة حاليًا |
| عدم إضافة قاعدة لمجرد الاتصال | موصى به | تُختار وفق حاجة بيانات محددة |
| عدم توحيد كل البروتوكولات في interface واحدة | موصى به | يحافظ على semantics والأمان الخاص بكل ناقل |

## 16. سجل قرارات الاتصال البشرية

لا يعني توثيق خيار اعتماده. الحالات هي `NOT_DECIDED` أو `NEEDS_VALIDATION` أو
`APPROVED`، ولا توجد حالة `APPROVED` في هذه المسودة.

| القرار المطلوب | الخيارات المعروفة | الأثر | ما هو موثق | ما يحتاج تحققًا/موافقة | الحالة |
|---|---|---|---|---|---|
| نمط الرد الأول | HTTP كامل؛ SSE لاحقًا | SSE يضيف اتصالات طويلة وresume/cancel وحدود event | HTTP يكفي العقد الحالي، وSSE أنسب من WebSocket للبث الأحادي | متطلب UX وقياس الكمون ودعم streaming لدى المزود | `NOT_DECIDED` |
| وجود مهام طويلة | طلب تابع للاتصال؛ مهمة مستقلة | يحدد التخزين والإلغاء والحالة والحاجة إلى queue | لا توجد مهام durable معتمدة حاليًا | حالات استخدام ومدة/SLA وملكية المهمة | `NOT_DECIDED` |
| الهوية والمصادقة | جلسة؛ token؛ بوابة مُدارة | عزل المستخدمين والإبطال وCSRF والتكلفة | المصادقة مطلوبة قبل API عامة | جمهور المنتج والاستضافة وthreat model | `NOT_DECIDED` |
| الموافقات | لكل عملية؛ لكل مورد ولمدة قصيرة | يمنع أثرًا غير مقصود ويضيف احتكاك UX | العمليات الحساسة تحتاج موافقة محددة | قائمة العمليات، نص الموافقة، expiry والإلغاء | `NOT_DECIDED` |
| سياسة خروج البيانات | deny؛ allowlist حسب التصنيف والمزود | الخصوصية والامتثال وجودة السياق | `restricted` لا يخرج لمزود غير مناسب | مصفوفة provider/tier × classification وموافقة المالك | `NOT_DECIDED` |
| أدوات محلية/بعيدة | لا أدوات؛ MCP stdio؛ MCP HTTP | sandbox وصلاحيات وtool poisoning وتشغيل إضافي | MCP مؤجل ولا توجد حاجة معتمدة | use cases وregistry وsandbox والموافقات | `NOT_DECIDED` |
| مخزن الحالة والحدود | لا تخزين دائم محليًا؛ DB/Key-Value مُدار | التكلفة والتوافر وفصل tenant وrate limit موزع | ذاكرة العملية والقرص المؤقت غير كافيين للعامة | منصة الاستضافة وSLA ومخطط البيانات | `NOT_DECIDED` |
| idempotency | بلا إعادة للكتابات؛ مخزن مفاتيح موزع | يمنع التكرار لكنه قد يحفظ hashes/نتائج حساسة | العمليات ذات الأثر لا تعاد بلا deduplication | العمليات المؤهلة وTTL والتشفير | `NOT_DECIDED` |
| سجل التدقيق | metadata محدود؛ مخزن append-oriented | التحقيق والخصوصية والتكلفة والاحتفاظ | prompts/secrets ممنوعة افتراضيًا | retention، readers، deletion وtamper evidence | `NOT_DECIDED` |
| حدود التكلفة والإيقاف | provider cap؛ prepaid؛ gateway kill switch | منع الإنفاق والانقطاع المقصود للخدمة | tokens/rate/alerts ليست hard cost cap | إمكانات الحساب الفعلي والمالك المناوب واختبار الإيقاف | `NOT_DECIDED` |
| طبيعة المنتج | شخصي محلي؛ عام غير تجاري؛ تجاري متعدد المستخدمين | يغير الاستضافة والشروط والهوية والامتثال | بعض الخطط تقيد الغرض التجاري | قرار صاحب المشروع والجمهور المستهدف | `NOT_DECIDED` |
| trusted proxy | اتصال مباشر؛ قائمة proxies موثوقة | دقة IP والحدود ومنع spoofing | لا ثقة في forwarded headers افتراضيًا | topology الفعلية ووثائق المنصة واختبارها | `NOT_DECIDED` |

أي انتقال إلى `NEEDS_VALIDATION` أو `APPROVED` يجب أن يسجل صاحب القرار والتاريخ
والدليل. نجاح اختبار محلي أو وجود خيار في وثيقة لا يكفي للاعتماد.

## 17. التوصية الصغيرة القابلة للتنفيذ بعد الاعتماد

لا يُنفذ ناقل جديد الآن. بعد حسم المزود والاستضافة والمصادقة، تُكتب مواصفة قصيرة
لعقد HTTP الحالي تشمل `request_id` وdeadline وحدود الأخطاء دون تغيير سلوك المنتج.
إذا اعتمدت المراجعة البشرية أن البث أولوية فعلية، تكون الدفعة التالية تصميمًا
واختبارًا محدودًا لـSSE لمسار المحادثة فقط، مع إلغاء وheartbeat وحدود event، بدل
إدخال WebSocket أو MCP أو وسيط رسائل مبكرًا.

هذه الوثيقة لا تثبت تنفيذ أي بروتوكول أو ضمان تشغيلي؛ كل بند تنفيذي يحتاج قرارًا
واختبارات وتهديدات خاصة به في دفعة مستقلة.
