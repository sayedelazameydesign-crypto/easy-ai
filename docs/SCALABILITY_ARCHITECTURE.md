# Cela.sh — Scalability Architecture Baseline

> **الحالة:** مسودة معمارية للمراجعة البشرية؛ ليست دليلًا على تنفيذ autoscaling أو
> اجتياز اختبارات حمل.
>
> **التاريخ:** 2026-10-08
>
> **النطاق:** متطلبات قابلية التوسع للـBackend والتخزين وموصلات المزود دون اعتماد
> منصة سحابية أو إضافة خدمات احترازية.

## 1. القرار المعماري

يبدأ Cela.sh كـ**modular monolith** بحدود داخلية واضحة، وليس مجموعة microservices.
هذا يحقق قابلية الاستبدال والاختبار دون إدخال شبكة داخلية أو وسيط رسائل أو اتساق
موزع قبل ظهور حاجة مثبتة.

مسار التوسع المقصود:

1. قياس الحمل والاختناقات أولًا.
2. تحسين الحدود والطلبات المكلفة ضمن سقف زمني ومالي.
3. توسع رأسي محدود عندما يكون أبسط وأقل تكلفة.
4. نسخ Backend عديمة الحالة للتوسع الأفقي.
5. استخراج مكوّن مستقل فقط إذا أثبت القياس أن له نمط حمل أو عزلًا أو ملكية مختلفة.

لا تعتمد هذه الوثيقة مزود استضافة أو قاعدة بيانات أو خدمة autoscaling. تظل القيم
الفعلية وحدود المنصة `NOT_DECIDED` حتى التحقق من الوثائق والحساب واختبار الحمل.

## 2. أهداف ومؤشرات التوسع

لا تعني قابلية التوسع “طلبات غير محدودة”. قبل الإنتاج يجب اعتماد workload model
يتضمن:

- الطلبات في الثانية والمتزامنة، ومعدل الذروة ومدتها ومعدل النمو المتوقع.
- توزيع أحجام prompts والردود والملفات وعدد الأدوات في الطلب.
- زمن استجابة p50 وp95 وp99 لكل operation.
- CPU والذاكرة واتصالات قاعدة البيانات وqueue depth.
- tokens في الدقيقة واليوم، وحدود مزود النموذج و429.
- التكلفة لكل طلب ناجح ولكل مستخدم/tenant وفترة فوترة.
- نسبة cache hit إن أُضيف cache، مع صحة الإبطال.

Capacity target وذروة الحمل وheadroom وSLO: `NOT_DECIDED`. لا تُعلن سعة قبل اختبار
ممثل للإنتاج ضمن حدود مصرح بها.

## 3. حدود المكونات المعيارية

### 3.1 الحدود المنطقية

يبقى التطبيق وحدة نشر واحدة مبدئيًا، مع فصل العقود بين:

- **HTTP/API boundary:** التحقق والمصادقة والحجم والمهلة وربط `request_id`.
- **Application orchestration:** حالة الطلب، الإلغاء، والسياسات المشتركة.
- **Provider adapter:** ترجمة عقد التطبيق إلى عقد مزود النموذج.
- **Policy and quota:** التفويض والحصة والحد المالي وkill switch.
- **Persistence ports:** الجلسة والمحادثة والتدقيق والحصة، دون ربط منطق المنتج
  بمحرك تخزين بعينه.
- **Tool connectors:** قدرات محدودة بعقود وصلاحيات مستقلة.
- **Observability:** metrics وlogs وtraces منقحة خارج منطق العمل.

لا يعني هذا الفصل إنشاء repositories أو packages جديدة فورًا؛ يُطبق تدريجيًا عند
تغيير الشيفرة، مع الحفاظ على العقود والاختبارات الحالية.

### 3.2 قواعد الاعتماد

- طبقة المجال لا تستورد SDK المزود أو إطار HTTP.
- الـadapter يعتمد contract داخليًا صغيرًا ومحدد الإصدارات.
- لا يصل connector مباشرة إلى جلسة مستخدم أو secret لا يحتاجه.
- configuration تُحقن عند حد التشغيل ولا تُقرأ عشوائيًا من البيئة داخل كل مكوّن.
- الأخطاء الخارجية تتحول إلى taxonomy داخلي ثابت دون كشف جسم المزود.
- تغيير مزود أو تخزين لا يغير عقد العميل إلا عبر إصدار ومراجعة صريحة.

### 3.3 متى يُستخرج مكوّن إلى خدمة مستقلة؟

يلزم دليل على واحد أو أكثر من الآتي:

- نمط حمل مستقل لا يمكن عزله داخل process بكفاءة.
- حاجة scaling أو failure domain مختلفة جذريًا.
- متطلبات أمن أو بيانات تمنع المشاركة.
- دورة نشر وملكية تشغيلية مستقلة فعليًا.
- مهمة طويلة تحتاج queue دائمًا وسلوك تسليم موثقًا.

قبل الاستخراج يجب توثيق latency والاتساق وauthentication والتدقيق وbackpressure
والفشل الجزئي والتكلفة. لا SSE أو MCP أو WebSocket أو gRPC أو message broker لمجرد
احتمال الحاجة.

## 4. التوسع الرأسي

التوسع الرأسي مناسب كخطوة أولى عندما يكون الحمل صغيرًا أو الاختناق محليًا:

- زيادة CPU لعمل محلي مثبت بأنه CPU-bound.
- زيادة الذاكرة فقط بعد قياس working set والتسرب والـcache.
- زيادة IOPS أو حجم التخزين وفق قياس، لا بدل إصلاح query سيئ.
- ضبط worker count وفق CPU وطبيعة I/O وحد اتصالات قاعدة البيانات.

الضوابط:

- لا يعتمد التصميم على ذاكرة أو قرص لا يمكن توفيرهما في الفئة التالية للمنصة.
- توثق حدود الحجم الأقصى وزمن restart والتكلفة.
- لا تُستخدم ذاكرة أكبر لإخفاء queue غير محدودة أو leak.
- vertical scaling له سقف؛ الوصول إليه يفعّل خطة horizontal scaling أو إعادة تصميم
  للاختناق المحدد، لا إعادة كتابة عامة.

## 5. التوسع الأفقي

### 5.1 Backend عديم الحالة

حتى تقبل عدة نسخ الطلبات بأمان:

- لا تُخزن الجلسة أو الحصة أو idempotency keys في ذاكرة process للإنتاج العام.
- لا يعتمد الطلب على filesystem محلي مؤقت.
- تبقى الأسرار والإعدادات خارج image وتُحقن لكل بيئة.
- كل instance يمكن إزالته دون فقد بيانات مع drain للطلبات الجارية.
- background work، إن ظهر، لا يبدأ في كل replica بلا leader/lease أو queue دائم.

### 5.2 توزيع المرور

- load balancer مُدار مرشح بعد اختيار المنصة، مع TLS وhealth checks صحيحة.
- readiness تمنع المرور قبل تهيئة الاعتماديات اللازمة.
- connection draining له مدة أقل من deadline الأعلى للطلبات.
- لا sticky sessions افتراضيًا؛ إن لزمت فهي حل مؤقت موثق وليست بديلًا للتخزين
  المشترك.
- خوارزمية التوزيع تُراجع مع الطلبات الطويلة؛ round-robin وحده قد لا يعكس العمل.

### 5.3 التزامن والاتساق

- limits موزعة حسب المستخدم/tenant، لا عدادات process منفصلة.
- quota وhard cost cap يُتحقق منهما ذريًا بالقدر الذي يمنع التجاوز غير المحدود.
- idempotency وdeduplication مشتركان بين النسخ.
- optimistic concurrency أو معاملات قصيرة لتحديثات الكتابة المتنافسة.
- لا قفل موزع مخصص قبل فحص primitives قاعدة البيانات أو الخدمة المُدارة.

## 6. توسع طبقة البيانات

ترتيب التحسين:

1. قياس query latency وخطط التنفيذ ومعدل الاتصالات.
2. indexes مبررة بالاستعلامات الفعلية ومراقبة تكلفة الكتابة.
3. pooling محدود بحيث لا تضاعف replicas الاتصالات فوق حد قاعدة البيانات.
4. pagination وحدود حجم؛ لا scans أو exports غير محدودة.
5. أرشفة/retention وفق سياسة البيانات، لا احتفاظ دائم افتراضي.
6. read replicas فقط للقراءات التي تقبل التأخر.
7. partitioning بعد إثبات حجم أو contention يبرره.
8. sharding كخيار أخير مع خطة routing وrebalancing واستعادة واضحة.

لا تُقرأ بيانات التفويض أو الحصة أو idempotency من replica متأخرة إذا كان التأخر
يسمح بتجاوز أمني أو مالي. التخزين المختار ومخططه وحدوده: `NOT_DECIDED`.

## 7. المرونة السحابية وAutoscaling

### 7.1 الإشارات

لا يعتمد autoscaling على CPU وحده. الإشارات المرشحة:

- الطلبات المتزامنة لكل instance.
- queue depth وعمر أقدم مهمة، إذا وُجدت queue معتمدة.
- p95 latency ومعدل saturation.
- CPU/ذاكرة كإشارات دعم.
- حدود اتصالات قاعدة البيانات وحصة المزود.

لا يجوز أن يزيد التطبيق replicas عندما يكون الاختناق 429 من المزود أو قاعدة بيانات
مشبعة؛ ذلك يوسع الضرر والتكلفة بدل السعة.

### 7.2 الحدود الآمنة

أي سياسة autoscaling يجب أن تحدد:

- min/max replicas وسقفًا ماليًا.
- target utilization ومدة التقييم.
- cooldown وstabilization window لمنع oscillation.
- سرعة scale-out وscale-in منفصلتين.
- readiness وstartup time وwarm-up behavior.
- drain وحماية العمل الجاري عند scale-in.
- تنبيهًا عند بلوغ الحد الأقصى أو فشل provisioning.

الحد الأدنى قد يكون صفرًا لبيئة تطوير تسمح cold start، لكنه لا يصلح تلقائيًا لـSLO
عام. الحد الأقصى لا يتجاوز قدرة قاعدة البيانات أو quota المزود أو hard cost cap.

### 7.3 Predictive وScheduled Scaling

يُقيّم scheduled scaling فقط بعد ظهور نمط دوري ثابت. predictive scaling مؤجل حتى
وجود بيانات تاريخية كافية، ومراجعة أخطاء التنبؤ والتكلفة. لا يُستخدم أي منهما بدل
حماية overload داخل التطبيق.

## 8. Backpressure وحماية الحمل الزائد

- حد مبكر لحجم body وprompt والملفات وعدد العمليات.
- concurrency limit عالمي ولكل tenant/operation.
- queue محدودة فقط إذا كانت دلالات الانتظار والإلغاء والتسليم موثقة.
- رفض سريع بـ429 أو 503 مناسب مع `Retry-After` بدل انهيار بطيء.
- deadline budget يمتد عبر المكونات ولا يُعاد ضبطه في كل hop.
- retry budget جزء من الحمل والحصة والتكلفة.
- load shedding يحمي عمليات الصحة والإدارة والأعمال الأعلى أولوية بسياسة معتمدة.
- circuit breaker لا يعوض limits أو timeouts ولا يتحول إلى cache لنجاح زائف.

تظل CORS خارج نموذج التحكم في الاستهلاك، ولا يُثق بـ`X-Forwarded-For` إلا من proxy
معتمد وبعد اختيار الاستضافة.

## 9. Caching

لا يُضاف cache قبل تحديد هدف ومعدل hit متوقع وسياسة صحة:

- cache key يشمل tenant والهوية وكل مدخل يؤثر في النتيجة.
- لا caching لقرارات التفويض دون إبطال وزمن قصير موثق.
- prompts والردود قد تحتوي بيانات حساسة؛ التخزين المؤقت يحتاج تصنيفًا وتشفيرًا
  وretention وموافقة مناسبة.
- يمنع cache stampede عبر request coalescing أو jittered TTL عند الحاجة.
- negative caching محدود ولا يخفي تعافي الاعتماد.
- cache ليس مصدر حقيقة ولا بديلًا للنسخ الاحتياطي.

نتائج النموذج غير الحتمية لا تُعاد لمستخدم آخر لمجرد تشابه النص. لا cache موزع قبل
إثبات أن فائدته تتجاوز التكلفة والمخاطر.

## 10. تكامل مزود النموذج والتكلفة

- provider adapter يطبق timeout وحجمًا وحدود tokens صريحة.
- 429 وquota exhaustion لا تُعالج بزيادة replicas.
- كل مستخدم/tenant له حصة، وكل عملية لها سقف tokens وتكلفة.
- autoscaling مقيد بالـhard spending cap وkill switch.
- batch أو async requests لا تُستخدم قبل توثيق الاحتياج والخصوصية والمهلة.
- fallback لمزود ثانٍ `NOT_APPROVED` حتى مراجعة العقود والبيانات والتكلفة والجودة.
- لا يُفترض أن مستوى مجاني يحقق سعة إنتاج أو SLA.

يجب فصل زمن التطبيق عن زمن المزود في القياسات كي لا يؤدي تحسين طبقة خاطئة إلى
تعقيد دون أثر.

## 11. الرصد وتخطيط السعة

Dashboard التوسع يجب أن يربط:

- traffic وconcurrency وlatency وerrors وsaturation.
- replicas المطلوبة والجاهزة وعمليات scale وأسبابها.
- CPU والذاكرة والاتصالات والـI/O والqueue depth.
- 429 و5xx والمهلات لكل dependency.
- tokens والحصة والتكلفة لكل operation/tenant ضمن ضوابط الخصوصية.
- headroom والتوقع حتى بلوغ حدود المنصة أو التخزين أو المزود.

تراجع السعة قبل أحداث متوقعة وبعد كل تغيير كبير وعند استهلاك headroom متفق عليه.
لا labels غير محدودة في metrics، ولا user IDs أو prompts كأبعاد عالية الكثافة.

## 12. الاختبار والتحقق

قبل اعتماد السعة أو autoscaling يلزم:

- baseline test لإصدار وبيئة وإعدادات موثقة.
- load test بحمل واقعي وتدرج حتى الهدف، لا طلبات صغيرة متجانسة فقط.
- stress test لمعرفة نقطة الانهيار والسلوك عند overload.
- spike test لإثبات سرعة scale-out وحدود cold start.
- soak test لاكتشاف leaks وتراكم الاتصالات والـqueues.
- scale-in test مع طلبات جارية وإلغاء وإغلاق آمن.
- database pool test مع عدد replicas الأقصى.
- quota/cost test يثبت توقف الزيادة عند الحدود.
- dependency test لـ429 والبطء والفشل الجزئي دون ضرب خدمة خارجية بغير تصريح.

بيانات الاختبار غير حساسة. تُنفذ اختبارات المزود الحقيقي فقط بموافقة ومفتاح وحد
مالي، ولا تعتبر mocks إثباتًا لسعة المنصة. غياب الاختبار يعني `NOT_TESTED`.

## 13. سجل القرارات

| القرار | الحالة | المطلوب للحسم |
|---|---|---|
| نمط البداية modular monolith | `PROPOSED` | مراجعة بشرية مع الحفاظ على العقود الحالية |
| منصة الاستضافة | `NOT_DECIDED` | تحقق رسمي وتجربة حساب فعلية |
| workload وcapacity target | `NOT_DECIDED` | بيانات استخدام وتوقع منتج |
| instance size وworker model | `NOT_DECIDED` | profiling وload test |
| min/max replicas | `NOT_DECIDED` | SLO وحدود DB والمزود والتكلفة |
| قاعدة البيانات وpool limits | `NOT_DECIDED` | تصميم البيانات وقياس الاستعلامات |
| distributed rate/quota store | `NOT_DECIDED` | اختيار الهوية والاستضافة والتخزين |
| cache موزع | `NOT_APPROVED` | قياس hit rate وحاجة مثبتة ومراجعة بيانات |
| queue/worker مستقل | `NOT_APPROVED` | مهمة طويلة ودلالات تسليم مثبتة |
| microservices | `NOT_APPROVED` | حدود حمل/ملكية/عزل لا يحلها التطبيق المعياري |
| multi-region active-active | `NOT_APPROVED` | SLO وRTO/RPO يبرران التعقيد |
| readiness للإطلاق العام | `BLOCKED` | إغلاق بوابات القسم التالي |

## 14. بوابات الإطلاق

### مسموح الآن

- الحفاظ على Backend محلي محدود ببيانات اختبار غير حساسة.
- تحسين الحدود الداخلية واختبارها دون تغيير عقود العميل.
- profiling وbenchmark محليان دون ادعاء سعة إنتاج.

### مانع للإطلاق العام

- workload model وSLO وcapacity target غير معتمدة.
- المصادقة والحصة الموزعة والحد المالي وkill switch غير منفذة ومختبرة.
- التخزين الدائم وpool limits وidempotency عبر النسخ غير محسومة.
- لا load/stress/spike/soak tests ممثلة وموثقة.
- لا سياسة autoscaling مثبتة ضمن حدود DB والمزود والتكلفة.
- بوابات الأمن والموثوقية والخصوصية ما زالت مفتوحة.

### شرط تغيير الحالة

لا تصبح قابلية التوسع `APPROVED` بمجرد إضافة replicas أو إعداد autoscaling. يلزم
تقرير اختبار مؤرخ يوضح البيئة والنسخة والحمل والنتائج والتكلفة ونقطة الانهيار، مع
قبول بشري للمخاطر والحدود المتبقية.

## 15. العلاقة مع الوثائق الأخرى

- `AI_BACKEND_DESIGN.md`: مزود النموذج والحدود المالية وعقد الـBackend.
- `COMMUNICATION_ARCHITECTURE.md`: المهل والإلغاء والـbackpressure ودلالات النقل.
- `SECURITY_ARCHITECTURE.md`: IAM والأسرار وعزل tenant والخصوصية.
- `RELIABILITY_ARCHITECTURE.md`: SLO والتوافر والنسخ الاحتياطي وDR وfailover.

عند التعارض تُطبق القاعدة الأكثر تحفظًا حتى قرار بشري. لا تغير هذه الوثيقة بنية
`sync/` أو حالات المزامنة أو عقود التخزين أو manifest، ولا تعتمد خدمة جديدة.
